# Тесты и ручные инструменты

В `tests/` два вида кода, и граница между ними проведена папкой:

| Где | Что | Кто запускает |
|---|---|---|
| `tests/` | юнит-тесты на Unity (`vendor/unity/`): `test_<модуль>.c` на модуль и `replay_test.c` | CTest, `check.sh`, `pre-push` |
| `tests/manual/` | инструменты для проверки руками: работают с живыми процессами в реальном времени, и решение «работает или нет» по их выводу принимает человек или агент | человек или агент |

И то и другое собирается в `build/tests/` вместе с игрой. Ручные инструменты
собираются наравне с тестами: если правка API, на котором они стоят, их
ломает, это видно по сборке, а не через месяц, когда инструмент понадобится.

Утилиты для графики в корневом `tools/` — другое: они не делят с игрой ни
строчки кода и собираются только с `-DBUILD_TOOLS=ON`
(`docs/assets-spec.md`).

## Запуск

```bash
ctest --test-dir build --output-on-failure           # все тесты
ctest --test-dir build -R door --output-on-failure   # один набор
.claude/skills/check/check.sh                        # сборка, тесты, lint, smoke, покрытие
.claude/skills/coverage/coverage.sh                  # покрытие в build-cov/
```

## Юнит-тесты

**Что тестируется.** Только то, что работает без кадра: симуляция, ввод,
протокол, сеть, загрузчик листов. Рендер не тестируется, звук — только по
длине синтезированных чанков (`test_audio.c`, драйвер `dummy`). Почему —
в `docs/closed_tasks/test-001-unit-test-harness.md`. Что набор проверяет,
сказано в шапке его файла.

**Как добавить тест.**

- Файл `tests/test_<модуль>.c`, регистрация в `tests/CMakeLists.txt`:
  `doom_test(<модуль> SRC <файлы из src/>...)`. `FILE` — когда имя файла
  другое, как у `replay_test.c`; `LINK` — библиотеки, например `doom_enet`.
- Тест линкует только нужные ему исходники, а остальное подменяет
  заглушками. Так `test_enemy.c` обходится без `sprite.c`, а через него — без
  рендера.
- Тест сетевого модуля регистрируется внутри `if(ENABLE_MULTIPLAYER)`:
  сборка без сети его не видит.
- Карту тест пишет сам в свой рабочий каталог (`build/tests/`), как
  `replay_test.c`. Клиенту нужна карта в `assets/maps/`: этот каталог рядом
  с тестом заводит `tests/CMakeLists.txt`.
- Изменение `src/` приходит со своими тестами. Какие изменённые строки не
  исполняет ни один тест, показывает `coverage.sh changed` (и `check.sh`).
  Пороги покрытия — храповик: их поднимают и никогда не опускают.

**Сеть.** Транспорт, сервер и клиент тестируются по настоящим сокетам на
127.0.0.1, всё в одном процессе: сервер и боты, которые говорят на протоколе
вручную, опрашиваются по очереди.

- Таймауты проверяются сдвигом часов ENet (`enet_time_set()`), а не
  ожиданием.
- Ждут тесты условия, а не числа тиков: в какой опрос придёт датаграмма,
  решает операционная система.
- У каждого набора свои порты, потому что `ctest -j` гоняет наборы
  параллельно: `test_net_transport` — 27115, `test_net_server` — 27116,
  `test_net_client` — 27117–27119. Порт игры по умолчанию (27015) тесты не
  трогают.

**Детерминизм.** `replay_test.c` дважды прогоняет одну последовательность
вводов от одного `world_load()` и требует побитово одинакового мира
(`docs/requirements.md`, §9). Его успех значит «два прогона совпали», а не
«результат верен».

## Ручные инструменты

Запускаются из корня проекта: карту клиент и сервер открывают по
относительному пути `assets/maps/`. Подробности — в шапке каждого файла.
Как вести с ними сетевую игру без экрана (дисплеи для клиентов, ловушки),
написано в `.claude/skills/run-doom-clone/SKILL.md`, раздел «Network game».

| Инструмент | На какой вопрос отвечает | Пример |
|---|---|---|
| `net_echo` | работает ли транспорт между двумя процессами: эхо, `kill -9` одной из сторон, частота цикла с `net_poll()` | `build/tests/net_echo server`, затем `build/tests/net_echo client 127.0.0.1` |
| `net_serve` | сервер для клиентов с окном (`doom-clone --connect`), пока игра сама не умеет им быть (07-07); с `--stats` раз в секунду печатает тики, время тика и опоздание | `build/tests/net_serve --stats` |
| `net_bot look` | что сейчас в мире у сервера: где игроки, кто из врагов мёртв, открыта ли дверь, лежит ли предмет; с `--rate` — тики, снапшоты и трафик в секунду | `build/tests/net_bot look --rate 3` |
| `net_bot run` | что будет после действий игрока: дойти, убить врага, открыть дверь — с точным прицелом, без окна и клавиатуры | `build/tests/net_bot run go 3.5 12.5 kill 1` |
| `net_bot swarm` | как сервер и клиенты держат нагрузку: N игроков ходят и стреляют, раз в секунду печатается трафик одного | `build/tests/net_bot swarm 9 60` |

Бот — настоящий игрок: он занимает слот, и враги на него нападают.

**Как добавить инструмент.** Инструмент, которым проверялась задача,
коммитится вместе с ней, если он ходит через API проекта и ответит на
вопрос, который ещё возникнет (`CLAUDE.md` → Conventions). Сначала
проверить, не ложится ли он режимом в уже имеющийся. Если нет — файл
`tests/manual/<имя>.c` с шапкой «что делает и как запускать» и строка
`doom_manual(<имя> SRC <файлы из src/>...)` в `tests/CMakeLists.txt`. В любом
случае — строка в таблице выше, а если агентам нужно знать, когда его
брать, — в `SKILL.md` скилла `run-doom-clone`.
