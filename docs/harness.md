# Харнесс Claude Code

Харнесс — всё, через что Claude Code работает с этим проектом: инструкции,
субагенты, скиллы, хуки, скрипты проверок и плагины. Почти всё лежит в
репозитории и версионируется вместе с кодом; что живёт вне его — на уровне
пользователя, — отмечено отдельно.

Документ — справочник: что есть, как это вызвать и почему оно устроено
именно так. Правила для самого Claude — в `CLAUDE.md`, подробности каждого
инструмента — в его `SKILL.md` или файле агента.

## Шпаргалка: что сказать Claude

| Хочу | Что написать | Что произойдёт |
|---|---|---|
| Сделать задачу целиком | «сделай задачу 07-01» или `/task 07-01` | скилл `task`: реализация, проверки, ревью, закрытие задачи, коммит (без push) |
| Завести задачу или баг | «заведи задачу: …», «запиши баг: …» | агент `project-manager` пишет файл в `docs/tasks/` и строку в индекс; не коммитит |
| Быстро проверить правки | «прогони check.sh» | сборка, тесты, lint, smoke, покрытие изменённых строк — ~15 с, без агентов |
| Полное ревью правок | «попроси ревьюера проверить текущие правки по задаче 07-01» | агент `reviewer`, который сам запускает `tester` |
| Только проверку в работе | `/verify docs/tasks/07-01-….md двери открываются с E` | агент `tester` в отдельном контексте |
| Закоммитить | «закоммить», «разбей на два коммита» | скилл `git-commit`: сообщение 50/72, проверка до коммита |
| Разобраться с багом | «diagnose: …», «почему падает …» | скилл `diagnosing-bugs`: цикл воспроизведение → гипотеза → проверка |
| Посмотреть игру | «запусти игру и сделай скриншот меню» | скилл `run-doom-clone`: Xvfb, ввод через `xdotool`, снимки кадров |
| Узнать покрытие | «какое покрытие у door.c», «покрыты ли мои правки» | скилл `coverage` |
| Статический анализ | «прогони lint» | скилл `lint`: cppcheck и проверка, что симуляция и сетевой протокол обходятся без SDL |

Скилл вызывается двумя способами: командой `/имя` или обычной фразой —
Claude сам выбирает скилл по его описанию (`description` во frontmatter).
Исключение — `/verify`: он только ручной (см. «Скиллы»).

## Карта файлов

```
CLAUDE.md                         правила проекта, грузятся в каждую сессию
.claude/
├── settings.json                 хук после правок, включённый плагин clangd-lsp
├── hooks/post-edit.sh            сам хук
├── agents/
│   ├── project-manager.md        заводит задачи
│   ├── reviewer.md               ревью качества кода
│   └── tester.md                 проверка в работе
└── skills/
    ├── task/                     весь цикл задачи
    ├── check/check.sh            все механические проверки одним вызовом
    ├── verify/                   ручной запуск tester
    ├── lint/lint.sh              cppcheck + симуляция и протокол без SDL
    ├── coverage/coverage.sh      покрытие тестами (gcovr)
    ├── run-doom-clone/driver.sh  запуск и управление игрой без экрана
    ├── git-commit/               правила и проверка сообщений коммитов
    └── diagnosing-bugs/          методика отладки
.githooks/                        git-хуки: commit-msg, pre-commit, pre-push
docs/tasks/README.md              шаблон задачи и процедура закрытия
```

## `CLAUDE.md`

Загружается в контекст каждой сессии целиком, поэтому держится коротким: в
нём только правила и ловушки, которые Claude нарушил бы без подсказки, а
подробности — ссылками на `docs/` и скиллы. Самое важное в нём:

- общаться с пользователем по-русски, документацию писать по-русски, код и
  комментарии — по-английски;
- архитектурные инварианты, которых не проверяет компилятор (симуляция без
  SDL, детерминированный тик, сущности не удаляются, упаковка цвета);
- задача считается сделанной, когда она в `docs/closed_tasks/`, и делается
  через `/task`;
- найденный по ходу баг — новая задача через `project-manager`, а не правка
  в текущем диффе;
- никаких хешей коммитов нигде; коммиты 50/72 с префиксом типа и без
  `Co-Authored-By`.

Правило, которое должно выполняться каждый раз, лучше делать хуком или
скриптом, а не строкой в `CLAUDE.md`: инструкцию модель может пропустить,
хук — нет.

## Субагенты

Субагент — отдельный экземпляр Claude со своим контекстом, моделью и
набором инструментов, описанный в `.claude/agents/<имя>.md`. Он стартует
«с нуля»: не видит разговора, только промпт, который ему передали.

| Агент | Модель | Что делает | Кто запускает | Чего не делает |
|---|---|---|---|---|
| `project-manager` | sonnet | пишет task-файлы по шаблону из `docs/tasks/README.md`, сначала ищет пересечения с существующими задачами | основная сессия — по просьбе или когда нашёлся баг по ходу работы | не пишет код, не коммитит |
| `reviewer` | sonnet | критерии приёмки, lint, архитектурные инварианты, конвенции; запускает `tester` и вставляет его отчёт в свой | скилл `task` перед закрытием задачи или вы по просьбе | ничего не правит и не собирает, не выносит вердикт «принято/отклонено» |
| `tester` | sonnet | `check.sh`, сценарий в игре под конкретное изменение (в сетевом коде — сервер, клиенты и `net_bot`), разбор непокрытых строк, оценка того, поймают ли тесты поломку | `reviewer`; вручную — `/verify` | не правит код и тесты, не пишет недостающие тесты, а описывает их |

**Почему ревью разделено на двух агентов.** Ревьюер читает код, тестировщик
его запускает — как в жизни, где QA и код-ревью делают разные люди.
Тестировщик не может править (в его инструментах нет `Write` и `Edit`):
тот, кто проверяет изменение, не должен подгонять его под проверку.

**Находки, а не вердикт.** Отчёты помечают каждую находку меткой:
`[критерий]`, `[дефект]`, `[инвариант]`, `[конвенция]`, `[нет теста]` —
исправить; `[необязательно]` — на усмотрение. Ревьюер, которого попросили
искать пробелы, найдёт их и в хорошей работе, поэтому необязательные
находки не надо чинить все подряд.

**Сам по себе Claude агентов не запускает.** По умолчанию Claude Code
вызывает субагента, только если его об этом попросили. Ревью запускается
потому, что этого требуют `CLAUDE.md` и скилл `task`, — для модели это
постоянная просьба.

**Общие ресурсы.** Пока работает `check.sh` или тестировщик, им принадлежат
`build/`, `build-cov/` и X-дисплей `:99`: две сборки или два запуска игры
одновременно портят друг друга. Во время ревью ничего не собирать.

**Стоимость.** Ревью — самый дорогой шаг цикла. Замер на `chore-002`
(правка в одну строку, 2026-10-17): ревьюер ~37 тыс. токенов и 85 с,
тестировщик ~30 тыс. токенов и 36 с внутри этих 85 с. Задача, где
тестировщик проходит сценарий в игре, обойдётся дороже. Цифры
тестировщика до ревьюера не доходят — он получает только текст отчёта, —
их берут из транскриптов (см. «Память и транскрипты»).

## Скиллы

Скилл — папка `.claude/skills/<имя>/` с `SKILL.md` (инструкция, которую
Claude загружает, когда задача подходит под описание) и, если нужно,
скриптом. Скрипты можно запускать и самому из терминала.

| Скилл | Вызов | Что делает |
|---|---|---|
| `task` | `/task 07-01` или «сделай задачу …» | весь цикл задачи, см. ниже |
| `check` | «прогони проверки», `check.sh [REV]` | чистая сборка с подсчётом предупреждений, `ctest`, lint, `driver.sh smoke` (если дифф доходит до игры), покрытие изменённых строк; сводка в несколько строк, логи в `.run/check/`; код 0 — всё в порядке, 1 — проверка упала, 2 — не собралось или неверная ревизия |
| `verify` | только `/verify [задача] [что должно работать]` | запускает `tester` в отдельном контексте и ждёт отчёт |
| `lint` | `lint.sh all \| changed \| sim \| strict` | `all`/`changed` — гейт: cppcheck и проверка, что симуляция (список `SIM=`) и серверные файлы вне неё (`NOSDL=`, сейчас `net_protocol.c`, `net_server.c`, `options.c` и `session.c`; читаются с `-DENABLE_MULTIPLAYER`) компилируются без SDL и не подключают ни одного SDL-заголовка, любая находка — дефект; `changed` берёт `.c`, отличные от `HEAD`, и новые неотслеживаемые; `sim` — только проверка без SDL; `strict` — стилистика, рекомендательно; уже заведённые находки перечислены в его `SKILL.md` |
| `coverage` | `coverage.sh [run \| report \| html \| changed [REV]]` | покрытие тестами в отдельном дереве `build-cov/`; пороги — храповик, только вверх, хранятся в самом скрипте; `changed` — изменённые строки `src/`, которые не исполняет ни один тест |
| `run-doom-clone` | `driver.sh smoke \| start \| key \| hold \| turn \| shot \| diff \| status \| log \| stop` | сборка и запуск игры под Xvfb, ввод с клавиатуры, снимки кадров; ловушки (мышь без экрана не работает, клавиша короче кадра теряется) — в его `SKILL.md`. Сетевая игра — раздел «Network game» там же: сервер `doom-clone --host --dedicated`, клиенты на своих дисплеях, `net_bot look \| run \| swarm` для состояния сервера, действий по сценарию и нагрузки (исходники в `tests/manual/`). Статус-бар в состояниях, до которых в игре трудно дойти, рисует без окна `hud_shot` (тоже `tests/manual/`) |
| `git-commit` | «закоммить» | пишет сообщение по правилам и проверяет его `check-message.sh` до коммита; `--history N` проверяет последние коммиты |
| `diagnosing-bugs` | «diagnose», «почему не работает …» | цикл отладки: воспроизвести, сузить, гипотеза, проверка; шаблон скрипта цикла в `scripts/` |

**Почему `/verify` только ручной.** Если в проекте есть скилл с именем
`verify`, который модель может вызывать сама, Claude Code запускает его
перед каждым коммитом. Это полный прогон тестировщика на каждый коммит
вместо одного на задачу, поэтому во frontmatter стоит
`disable-model-invocation: true`.

## Цикл задачи: `/task`

1. Найти задачу; если она закрыта, неоднозначна или её зависимость ещё
   открыта — остановиться и сказать.
2. Сверить задачу с кодом: task-файлы пишутся заранее и устаревают. Если
   расхождение меняет решение — спросить.
3. Реализовать, прогоняя `check.sh` после каждого шага; тесты обновить в
   той же правке.
4. Самому пройти «Критерий готовности», чтобы не тратить ревью на заведомо
   незаконченную работу. Временные программы, написанные по ходу, разобрать:
   те, что ходят через API проекта и ответят на вопрос, который ещё
   возникнет, переносятся в `tests/manual/` до ревью, остальные остаются во
   временной папке.
5. Ревью: `reviewer` → `tester`; исправить обязательные находки, кандидатов
   в отдельные задачи отдать `project-manager`. Программу, которую tester
   назвал стоящей, взвесить так же, как свои. Повторное ревью — только
   если исправления поменяли решение.
6. Закрыть по «Как закрыть задачу» в `docs/tasks/README.md`: `git mv` в
   `docs/closed_tasks/`, раздел «Закрыто», строка в индексе, правка
   документов, которым изменение теперь противоречит.
7. Коммит через `git-commit`: работа и закрытие в одном коммите. Push не
   делается.
8. Отчёт по-русски: что сделано, итог `check.sh`, судьба каждой находки,
   заведённые задачи, какие временные программы вошли в `tests/manual/`, а
   какие нет, коммиты.

## Хуки

**Хук Claude Code** (`.claude/settings.json` → `.claude/hooks/post-edit.sh`)
срабатывает после каждого `Edit`/`Write`. Работает только на правки Claude,
не на ваши:

- `.c`/`.h` в `src/`, `tests/`, `tools/` прогоняет через `clang-format`;
- после правки в `src/` запускает `lint.sh sim` и, если симуляция или
  серверный файл из `NOSDL=` видит SDL, возвращает ошибку Claude (код 2) —
  он видит её сразу и исправляет.

**Git-хуки** в `.githooks/` выключены, пока их не включить в клоне:

```bash
git config core.hooksPath .githooks
```

| Хук | Что делает |
|---|---|
| `commit-msg` | проверяет сообщение тем же `check-message.sh` |
| `pre-commit` | не пускает застейдженные `src/*.c`/`*.h`, не отформатированные по `.clang-format`; файлы не переписывает |
| `pre-push` | сборка, `ctest`, `driver.sh smoke`, ~9 с |

`git commit --no-verify` / `git push --no-verify` их обходят.

## Плагины, MCP и внешние утилиты

**В репозитории:** плагин `clangd-lsp` (из официального маркетплейса
`claude-plugins-official`) включён в `.claude/settings.json`, так что в
любом клоне он включён для проекта; установлен ли он, зависит от машины
(см. «Новая машина»). Он даёт инструмент `LSP` основной
сессии, `reviewer` и `tester`: переход к определению, поиск ссылок,
`incomingCalls` — кто вызывает функцию, в том числе какие тесты.
`outgoingCalls` clangd 18 из Ubuntu не поддерживает. Флаги компиляции он
берёт из `build/compile_commands.json`: CMake пишет его при конфигурации и
ставит на него ссылку в корне проекта, так что IDE с clangd тоже видит
проект сразу после `cmake -S . -B build`.

**На уровне пользователя** (в репозитории их нет, на другой машине их
придётся подключать заново):

- MCP-сервер `context7` — актуальная документация библиотек (понадобится
  для ENet на этапе 7);
- MCP-сервер `sequential-thinking`;
- коннектор Claude Docs из claude.ai.

**`gh`** — CLI GitHub, вместо MCP-сервера GitHub: тратит меньше контекста.
Нужен для CI (`chore-001`) и PR; перед первым использованием —
`gh auth login`.

## Память и транскрипты

- **Авто-память** — `~/.claude/projects/<путь-проекта>/memory/`: по факту на
  файл, `MEMORY.md` — оглавление, которое грузится в каждую сессию. Туда
  попадает то, чего нет в коде и `CLAUDE.md`: предпочтения, замеры,
  решения. «Запомни, что …» — записать; «забудь …» — удалить.
- **Транскрипты сессий** — `~/.claude/projects/<путь-проекта>/<сессия>.jsonl`,
  субагентов — в `<сессия>/subagents/`. Оттуда берутся токены, число
  вызовов инструментов и длительность каждого агента.
- **Контекст сессии** сжимается автоматически, когда разговор становится
  длинным; работа продолжается по сводке.

## Что создаёт харнесс на диске

Всё ниже в `.gitignore` и удаляется без последствий — пересоздаётся при
следующем запуске.

| Путь | Кто создаёт | Что там |
|---|---|---|
| `build/` | CMake, `check.sh`, `driver.sh` | основная сборка, `compile_commands.json` |
| `compile_commands.json` | CMake | ссылка на `build/compile_commands.json` |
| `build-cov/` | `coverage.sh` | сборка тестов с `--coverage`, отчёты gcovr |
| `.run/` | `driver.sh` | лог игры, снимки кадров, pid Xvfb |
| `.run/check/` | `check.sh` | полный вывод каждого шага |
| `.cache/` | clangd | фоновый индекс |
| `raw/` | вы | сырые картинки от генеративной модели для `tools/` |

## Новая машина

```bash
sudo apt-get install -y cmake build-essential libsdl2-dev libsdl2-mixer-dev \
    xvfb xdotool imagemagick cppcheck clang-format gcovr jq python3 clangd
git config core.hooksPath .githooks
git submodule update --init              # vendor/enet, если клон без --recurse-submodules
cmake -S . -B build && cmake --build build
.claude/skills/check/check.sh            # всё должно быть «ок»
gh auth login                            # если нужен GitHub
```

Если `claude plugin list` не показывает `clangd-lsp`, установить его:
`claude plugin install clangd-lsp@claude-plugins-official` (или
`/plugin install …` внутри сессии) и перезапустить сессию.

## Как менять харнесс

- **Агент** — `.claude/agents/<имя>.md`: frontmatter (`name`, `description`,
  `tools`, `model`) и инструкция. По `description` основная сессия решает,
  когда агент подходит; `tools` ограничивает, что он может.
- **Скилл** — `.claude/skills/<имя>/SKILL.md`. `description` решает, когда
  Claude вызовет его сам; `disable-model-invocation: true` — только вручную;
  `context: fork` с `agent:` — выполнить в субагенте.
- **Хук** — `.claude/settings.json`, раздел `hooks`. Код 2 из хука
  возвращает его stderr Claude.
- **Один факт — одно место.** Список, который меняется (находки lint,
  пороги покрытия, шаги проверки), хранится в одном файле, а остальные на
  него ссылаются. Иначе каждая закрытая задача правит три файла, и
  какой-нибудь из них забудут.
- **Этот документ** обновляется вместе с любой правкой в `.claude/` и
  `.githooks/`.
