# Куда движется проект

Цель — превратить одиночное демо в сетевой deathmatch на 10 игроков.
Здесь целевая архитектура и обоснование решений; **конкретные работы с
критериями приёмки — в [tasks/](tasks/)**, и порядок их выполнения задаёт
граф зависимостей в [tasks/README.md](tasks/README.md), а не этот файл.

Как устроена игра сейчас — в [architecture.md](architecture.md).
Ограничения по производительности, задержке и платформам — в
[requirements.md](requirements.md).

## Целевая конфигурация

| Параметр | Значение |
|---|---|
| Сетевая модель | Authoritative server |
| Топология | Listen-server: хост = сервер + локальный клиент |
| Транспорт | UDP через ENet |
| Максимум игроков | 10 |
| Тикрейт симуляции | 60 Гц |
| Частота снапшотов | 20 Гц |
| Формат снапшота | Полное состояние мира, без дельта-компрессии |
| Предсказание | Client-side prediction + reconciliation |
| Лаг-компенсация | Откат на RTT/2 + interp, обязательна |
| Основной режим | Deathmatch, co-op вторым |
| Карта | 48×48, пул точек спавна |

## Этапы

Пять этапов, продолжающих нумерацию четырёх пройденных. Каждый проверяем
целиком, и первые два не трогают сеть вообще — они делаются и отлаживаются
в одиночной игре.

| Этап | Что делается | Итог |
|---|---|---|
| 5 | Развязка симуляции и рендера, мировой хитскан | симуляция считается без единого пикселя |
| 6 | Мультиплеерная логика без сети | игра логически многопользовательская |
| 7 | Сеть: транспорт, протокол, снапшоты | два клиента в одном мире |
| 8 | Качество netcode | интерполяция, предсказание, лаг-компенсация |
| 9 | Deathmatch, карта, меню | законченная игра на 2–10 человек |

Этап 5 — жёсткая предпосылка всего остального, а внутри него задача
«переписать хитскан на мировой рейкаст» блокирует почти всё.

## Ключевые решения

1. **Authoritative server, не lockstep.** Код на `float`; битовая
   идентичность вычислений между платформами не гарантируется, а
   детерминированный lockstep потребовал бы фиксированной точки и
   переписывания всей физики. Сервер как источник истины снимает вопрос
   детерминизма и попутно закрывает читы.

2. **Мировой хитскан — первым делом.** Сейчас попадание ищется по
   экранному AABB врага и глобальному Z-буферу, который заполняется при
   рендере. На сервере фреймбуфера нет, а при нескольких игроках Z-буфер
   принадлежит чужой камере. Пока это не переписано, сеть невозможна.

3. **Один `world_step()` на сервере и клиенте.** Предсказание работает,
   только если клиент переигрывает ровно ту же функцию, что и сервер.
   Любая ветка «на клиенте пропустим ИИ» внутри неё создаёт расхождение,
   которое проявится не сразу и будет искаться долго.

4. **`angle` вместо векторов `dir` и `plane`.** Плоскость камеры —
   артефакт рендера. Векторы направления нельзя корректно интерполировать
   между снапшотами, углы — тривиально. В пакете 1 float вместо 4.

5. **Полный снапшот вместо дельт.** Мир целиком укладывается примерно в
   1 КБ, при 20 Гц это до 20 КБ/с на клиента. Дельта-компрессия и
   битпакинг дают больше багов, чем экономии, пока игроков десяток.

6. **Спрайты — чисто клиентская сущность.** Клиент строит список спрайтов
   из состояния мира каждый кадр, а не наоборот.

7. **Индекс в массиве = сетевой id.** Списки фиксированные, элементы не
   удаляются — отдельная система идентификаторов не нужна.

8. **ENet, а не SDL2_net.** SDL2_net даёт голый UDP без надёжных каналов,
   фрагментации и учёта RTT. ENet — около 10 тысяч строк на C под ровно
   эту задачу, есть в пакетных менеджерах всех целевых платформ.

9. **`rand()` только на сервере.** Разброс дробовика — часть симуляции;
   если его крутит и клиент, предсказание разойдётся.

10. **Звук событиями, а не состоянием.** Сервер сообщает факт «выстрел в
    точке», громкость и панораму клиент считает от своего игрока.

## Риски

| Риск | Митигация |
|---|---|
| Экранный хитскан не переносится на сервер | Этап 5, до всего остального |
| Предсказание расходится с сервером | Единый `world_step()`; `rand()` только на сервере; отладочный оверлей с расхождением |
| Позиции предметов живут в спрайтах | Заполнить координаты в самих предметах на этапе 6 |
| Ввод привязан к кадру, а не к тику | Переделать на сэмплинг ввода на тик с номером тика |
| Сеть отлаживается одновременно с логикой | Этапы 5–6 полностью проверяемы без сокетов |
| `MAX_SPRITES` переполняется при 10 игроках | Поднять лимит на этапе 6 |
| Карта 24×24 тесна для 10 игроков | Карта 48×48 и пул точек спавна |
| Хитскан без лаг-компенсации не попадает | Лаг-компенсация обязательна, не опциональна |
| Спавн-килл | Пул точек, выбор дальней от живых, неуязвимость после респавна |

## Оценка объёма

| Этап | Объём |
|---|---|
| 5 — развязка и мировой хитскан | ~250–350 строк изменений |
| 6 — мультиплеерная логика локально | ~200–300 строк |
| 7 — сеть и снапшоты | ~700–900 строк нового кода |
| 8 — интерполяция, предсказание, лаг-компенсация | ~450–650 строк |
| 9 — deathmatch, карта, меню | ~450–600 строк |

Итого около 2–2.8 тысяч строк поверх текущих 2.4 тысяч: проект примерно
удваивается.

## Не запланировано

Идеи без сроков и без задач. Решив взяться — завести файл в
[tasks/](tasks/) с префиксом по роду работ (`feat-`, `test-`, `chore-`) и
убрать строку отсюда. Перед этим стоит проверить, не покрыта ли идея уже
существующей задачей.

- Текстурирование пола и потолка (floor casting) — зарезервировано ещё на
  этапе 2, так и не сделано
- Несколько карт и выбор карты в меню
- Ракурсы спрайта игрока: сейчас все «смотрят» на камеру, и в бою не
  понять, заметил тебя противник или нет

## Ресурсы

- **Gabriel Gambetta — Fast-Paced Multiplayer** — предсказание,
  реконсиляция, интерполяция; лучший вводный материал
- **Valve — Source Multiplayer Networking** — лаг-компенсация на практике
- **Glenn Fiedler — Gaffer On Games** — снапшоты, сериализация,
  надёжность поверх UDP
- **ENet documentation** (sauerbraten.org/enet) — API и модель каналов
- **Quake / QuakeWorld sources** — образец client-server с предсказанием
