# План разработки мультиплеера для Doom-клона

Продолжение [plan.md](plan.md). Недели 1–4 (одиночная игра) выполнены;
здесь — недели 5–9, превращение демо в сетевую игру на нескольких игроков.

Нефункциональные требования (производительность, бюджет задержки, лимиты,
платформы, тестирование) — в [requirements.md](requirements.md).

## Конфигурация мультиплеера

| Параметр | Значение |
|---|---|
| Сетевая модель | Authoritative server (сервер — источник истины) |
| Топология | Listen-server: хост = сервер + локальный клиент в одном процессе |
| Транспорт | UDP через **ENet** (MIT, чистый C) |
| Максимум игроков | 10 |
| Тикрейт симуляции | 60 Гц (существующий `FIXED_DT`) |
| Частота снапшотов | 20 Гц |
| Частота отправки ввода | 60 Гц (каждый тик) |
| Формат снапшота | Полное состояние мира, без дельта-компрессии |
| Размер снапшота | ~390 Б (DM) / ~990 Б (co-op с врагами) |
| Трафик | до 20 КБ/с вниз на клиента; до ~200 КБ/с вверх с сервера |
| Задержка интерполяции | 100 мс (2 снапшота) |
| Предсказание | Client-side prediction + reconciliation для своего игрока |
| Лаг-компенсация | Откат на RTT/2 + interp, история 1 с — **обязательна** |
| Порт по умолчанию | 27015/UDP |
| Основной режим | **Deathmatch** (враги выключены, PvP-урон) |
| Второй режим | Co-op (враги общие, PvP-урон выключен) |
| Лимит фрагов (DM) | 30, либо 10 минут |
| Респавн | 2 с + 2 с неуязвимости, пул точек спавна |

### Неделя 7 — Сеть: транспорт, протокол, снапшоты

- [ ] Подключить ENet в `CMakeLists.txt` (`find_package(enet)` + fallback
      на вендоринг в `vendor/enet/`)
- [ ] `net_transport.c/.h` — тонкая обёртка: `host_create`, `connect`,
      `send_reliable`, `send_unreliable`, `poll`
- [ ] `net_protocol.h` — версия протокола + структуры:
  ```c
  #define PROTO_VERSION 1

  /* клиент → сервер, каждый тик, unreliable */
  typedef struct {
      uint32_t tick;
      uint16_t buttons;  /* forward/back/strafe/fire/use/switch — битмаска */
      float    angle;    /* поворот считает клиент */
  } PlayerInput;

  /* сервер → клиент, 20 Гц, unreliable */
  typedef struct {
      uint32_t tick, last_input_tick;  /* last_input_tick — для реконсиляции */
      uint8_t  player_count, enemy_count, event_count;
      NetPlayer players[MAX_PLAYERS];  /* id,x,y,angle,hp,armor,weapon,ammo,alive */
      NetEnemy  enemies[MAX_ENEMIES];  /* x,y,hp,state,type */
      uint64_t  items_alive;           /* битовая маска подобранных */
      uint8_t   doors[MAX_DOORS];      /* openness, квантованный в байт */
      NetEvent  events[MAX_EVENTS];    /* выстрел/смерть/подбор + позиция */
  } Snapshot;
  ```
- [ ] Handshake (reliable): `JOIN{proto_version, name}` →
      `ACCEPT{your_id, map_name, seed}` либо `REJECT{reason}`; `DISCONNECT`
- [ ] `net_server.c` — тик 60 Гц, применяет последний полученный ввод каждого
      клиента, шлёт снапшоты 20 Гц; таймаут отключившихся
- [ ] `net_client.c` — шлёт ввод каждый тик, принимает снапшоты, применяет
      состояние «как есть» (интерполяция и предсказание — неделя 8)
- [ ] Аудио через события: сервер шлёт «выстрел в (x,y)», клиент считает
      дистанцию до **своего** игрока и зовёт существующий `audio_play()`
- [ ] `main.c` — режимы запуска: `--host`, `--connect <ip>`, без флагов — solo
- [ ] Опция сборки `-DSERVER_ONLY=ON` — headless-бинарь без SDL_video

**Результат:** два клиента в одном мире. Движение рывками (без интерполяции),
своё движение с задержкой на RTT — это чинится на неделе 8.

### Неделя 8 — Качество netcode

Без этого при пинге 50 мс управление ощущается вязким.

- [ ] **Интерполяция** чужих сущностей: кольцевой буфер на 3 снапшота,
      рендер с задержкой 100 мс, линейная интерполяция позиций и углов
      (углы — через кратчайшую дугу)
- [ ] **Предсказание своего игрока:** клиент применяет ввод локально сразу
      через `world_step()`, хранит историю неподтверждённых вводов
- [ ] **Реконсиляция:** при получении снапшота — откат на серверную позицию
      и переигрывание вводов новее `last_input_tick`; сглаживание расхождений
      меньше порога (0.05 клетки), чтобы не дёргать камеру
- [ ] Экстраполяция при потере пакетов (не более 250 мс)
- [ ] **Лаг-компенсация** хитскана (обязательна в DM): сервер хранит 1 с
      истории позиций, при выстреле откатывает мир на `RTT/2 + INTERP_DELAY`
      стрелявшего. Без неё хитскан-стрельба по движущимся игрокам не попадает
- [ ] Отладочный оверлей: пинг, потери, расхождение предсказания, размер
      снапшота (клавиша F3)
- [ ] Тест с искусственной задержкой (`tc netem` на Linux) — 50/150/300 мс

**Результат:** управление отзывчивое, чужие игроки движутся плавно.

## Ключевые технические решения

1. **Authoritative server, не lockstep.** Код на `float` (`sqrtf`, `cosf`,
   `sinf`); битовая идентичность float-математики между платформами не
   гарантируется, а детерминированный lockstep потребовал бы фиксированной
   точки и переписывания всей физики. Сервер как источник истины снимает
   вопрос детерминизма и попутно закрывает читы.
2. **Мировой хитскан — жёсткая предпосылка всего остального.** Сейчас
   `weapon.c:109` читает глобальный `zBuffer[screenX]`, заполняемый при
   **рендере**, а попадание ищется по экранному AABB спрайта
   (`enemy_screen_band()`). На сервере фреймбуфера нет, а при нескольких
   игроках zBuffer принадлежит чужой камере. Переписывается первым делом.
3. **Один `world_step()` на сервере и клиенте.** Предсказание работает только
   если клиент переигрывает ровно ту же функцию, что и сервер. Ради этого
   логика собирается в одну точку входа на неделе 6.
4. **`angle` вместо `dir`/`plane` в состоянии игрока.** Плоскость камеры —
   артефакт рендера (FOV), в сети ей не место. Векторы направления нельзя
   корректно интерполировать между снапшотами, углы — тривиально.
   4 float → 1 float в пакете.
5. **Полный снапшот вместо дельт.** 10 игроков (200 Б) + 32 врага (384 Б) +
   32 события (320 Б) + двери (64 Б) + маска предметов (8 Б) ≈ 990 Б —
   влезает в MTU без фрагментации. В DM врагов нет, снапшот ~390 Б.
   Битпакинг и дельта-компрессия не нужны: экономия не требуется, а багов
   они дают больше, чем любая другая часть netcode. Запас до 1500 Б
   контролировать `static_assert`.
6. **Спрайты — чисто клиентская сущность.** Сейчас `SpriteList` служит
   источником истины для позиций предметов (`item.c:62`) и зеркалом позиций
   врагов (`enemy.c:147`). Клиент должен строить спрайты из состояния мира,
   а не наоборот.
7. **Индекс в массиве = сетевой id.** Все списки — фиксированные массивы,
   элементы не удаляются (предметы деактивируются, враги становятся трупами).
   Отдельная система id не нужна.
8. **ENet, а не SDL2_net.** SDL2_net даёт голый UDP без надёжных каналов,
   фрагментации и учёта RTT. ENet — ~10k строк на C под ровно эту задачу,
   есть в apt/brew/vcpkg.
9. **`rand()` только на сервере.** Разброс дробовика (`weapon.c:84`) —
   часть симуляции; клиент не должен его крутить, иначе предсказание
   разойдётся с сервером.
10. **Звук — событиями, а не состоянием.** Сервер шлёт факт «выстрел в (x,y)»;
    громкость и панораму клиент считает от своего игрока. Существующий
    API `audio_play(a, id, dist, maxdist)` менять не нужно.

## Управление (дополнения)

| Клавиша | Действие |
|---|---|
| Tab | Скорборд, до 10 строк (неделя 9) |
| F3 | Отладочный оверлей сети: пинг, потери, расхождение (неделя 8) |
| T | Чат (опционально, если останется время) |

## Формат карты (дополнения)

```
s  - точка спавна (пул, 12-16 штук; неделя 9)
P  - точка старта одиночной игры (без изменений)
```

Точки спавна не закреплены за игроками: в deathmatch при каждом респавне
выбирается наиболее безопасная из пула. При запуске сетевой игры маркер `P`
игнорируется; если точек `s` на карте нет, они генерируются из свободных
ячеек.

`MAP_MAX_W/H` поднимаются с 24 до 48 (`utils.h:11-12`): 24×24 на 10 игроков
слишком тесно.

## Зависимости

К существующим SDL2 и SDL2_mixer добавляется ENet:

| ОС | Команда установки |
|---|---|
| macOS (Homebrew) | `brew install enet` |
| Linux (Debian/Ubuntu) | `sudo apt install libenet-dev` |
| Linux (Fedora) | `sudo dnf install enet-devel` |
| Windows (MSYS2/MinGW) | `pacman -S mingw-w64-x86_64-enet` |
| Windows (vcpkg/MSVC) | `vcpkg install enet` |

Fallback: положить исходники ENet в `vendor/enet/` и собирать вместе с
проектом — библиотека маленькая и не тянет зависимостей.

## Запуск

```bash
./build/doom-clone                        # одиночная игра (как сейчас)
./build/doom-clone --host                 # хост: сервер + локальный клиент
./build/doom-clone --connect 192.168.1.10 # подключиться к хосту
./build/doom-clone --host --dedicated     # headless-сервер без окна
```

Порт 27015/UDP должен быть открыт на машине хоста.

## Риски и подводные камни

| Риск | Митигация |
|---|---|
| Экранный хитскан не переносится на сервер | Неделя 5, до всего остального |
| Предсказание расходится с сервером | Единый `world_step()`; `rand()` только на сервере; отладочный вывод расхождения (F3) |
| Позиции предметов живут в спрайтах | Заполнить `Item.x/y` на неделе 6 |
| Ввод привязан к кадру, а не к тику | `input_end_frame()` вызывается внутри фикс-шага (`main.c:170`), `mouse_dx` копится за кадр — переделать на сэмплинг ввода на тик с номером тика |
| Сеть отлаживается одновременно с логикой | Недели 5–6 полностью проверяемы без сокетов |
| Двери/предметы рассинхронизируются | Состояние дверей и маска предметов входят в каждый снапшот целиком |
| `MAX_SPRITES 96` переполняется | 32 врага + 64 предмета + бочки + 9 чужих игроков ≈ 110 > 96 (`sprite.h:27`). Поднять до 192 на неделе 6 |
| Карта 24×24 тесна для 10 игроков | Спавн-килл и хаос гарантированы. `MAP_MAX` до 48 + DM-карта (задача 09-07) |
| Хитскан без лаг-компенсации в DM не попадает | Задача 08-05 обязательна к выполнению |
| Спавн-килл | Пул точек + выбор дальней от живых + 2 с неуязвимости после респавна |
| Всплеск событий при 10 игроках | `MAX_EVENTS 32` на снапшот переполнится; отбор по дистанции до получателя (07-06) |
