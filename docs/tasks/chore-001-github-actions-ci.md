## Контекст

`requirements.md`, раздел 1, делит платформы на тиры: Linux — тир-1,
проверяется при каждом изменении; macOS и Windows — тир-2, обязаны
собираться, полная проверка — в конце каждого этапа. Раздел 9 того же
документа перечисляет, что и когда прогонять; таблица «Ручная проверка»
там — единственный сегодня существующий механизм, и тир-2 в ней никто не
гоняет вообще, кроме как руками разработчика.

В `.githooks/` есть три хука (`pre-commit`, `commit-msg`, `pre-push`), но
все три:

- включаются вручную командой `git config core.hooksPath .githooks`
  (это не происходит само по себе при клонировании репозитория);
- обходятся флагом `--no-verify`;
- не выполняются вовсе для PR из форка или для человека, который просто не
  выполнил команду выше.

Значит они защищают того, кто их включил и не обошёл, а не репозиторий как
таковой — для PR это не гарантия.

Проверено на текущем дереве:

- `cmake -S . -B build && cmake --build build` даёт ровно два
  предупреждения, оба `-Wunused-function` в `vendor/stb_image.h` (строки
  1070 и 1078); код проекта в `src/` собирается чисто под `-Wall -Wextra`
  (эти флаги уже включены глобально, `CMakeLists.txt:13-15`, но без
  `-Werror` — предупреждение в `src/` сегодня не роняет сборку)
- `clang-format --dry-run -Werror src/*.c src/*.h` проходит без замечаний

Зависимостей сборки сегодня две — `SDL2` и `SDL2_mixer`
(`CMakeLists.txt:21-22`). ENet (задача `07-01-enet-build.md`) и `tests/`
(задача `test-001-unit-test-harness.md`) ещё не существуют, так что задача
не должна предполагать ни `-DENABLE_MULTIPLAYER`, ни `ctest` как что-то уже
работающее — только как то, что появится позже без переписывания workflow.

`.claude/skills/run-doom-clone/driver.sh smoke` — единственная сегодня
автоматическая проверка игрового цикла (сборка, меню, движение, поворот,
выстрел). Требует Xvfb, xdotool, ImageMagick
(`.claude/skills/run-doom-clone/SKILL.md`) — это Linux-инструменты; на
macOS и Windows headless-запуск SDL2-приложения устроен иначе и в проекте
не реализован, так что smoke на тир-2 сегодня не реалистичен.

Удалённый `origin` репозитория — `github.com:AlexEr92/doom-clone.git`, так
что GitHub Actions не требует ни отдельной регистрации, ни внешней
инфраструктуры и даёт нужные образы (`ubuntu-latest`, `macos-latest`,
`windows-latest`) без предварительной настройки — альтернативные
CI-провайдеры или self-hosted раннер обсуждать не за чем.

## Что сделать

- [ ] Завести `.github/workflows/ci.yml` с триггерами `push` и
      `pull_request` — соответствует требованию «при каждом изменении» из
      `requirements.md`, раздел 9
- [ ] Job `linux` (`runs-on: ubuntu-latest`, тир-1, обязателен на каждый
      пуш/PR):
  - установить зависимости сборки (`cmake`, `build-essential`,
    `libsdl2-dev`, `libsdl2-mixer-dev`) и зависимости smoke (`xvfb`,
    `xdotool`, `imagemagick`), плюс `clang-format`
  - шаг форматирования: `clang-format --dry-run -Werror src/*.c src/*.h`
    — тот же критерий, что в `.githooks/pre-commit`, но по всему `src/`,
    а не только по застейдженным файлам, и без возможности `--no-verify`
  - сборка: `cmake -S . -B build && cmake --build build`, вывод сохранить
    и проверить на предупреждения — `grep "warning:"` по логу не должен
    находить ничего за пределами `vendor/stb_image.h` (сегодня там ровно
    два `-Wunused-function`, см. «Контекст»); шаг явно проваливается,
    если появится предупреждение в `src/`, поскольку `-Werror` в
    `CMakeLists.txt` не включён
  - юнит-тесты: `ctest --test-dir build --output-on-failure` — наборы из
    `tests/` собираются вместе с игрой (опция `BUILD_TESTS` по умолчанию
    `ON`), отдельного шага сборки им не нужно
  - smoke: `.claude/skills/run-doom-clone/driver.sh smoke` — обязательный
    шаг (не пропускается при отсутствии Xvfb/xdotool, как в `pre-push`,
    поскольку на раннере они установлены явно шагом выше)
- [ ] Job `macos` (`runs-on: macos-latest`, тир-2, только сборка):
  - `brew install sdl2 sdl2_mixer`
  - `cmake -S . -B build && cmake --build build` — только факт успешной
    сборки, без разбора предупреждений (warning-free — требование только
    тир-1) и без smoke (см. «Контекст»)
- [ ] Job `windows` (`runs-on: windows-latest`, тир-2, только сборка):
  - установить `SDL2`/`SDL2_mixer` через vcpkg, который на
    windows-раннерах GitHub предустановлен (`$env:VCPKG_INSTALLATION_ROOT`)
    — точные имена пакетов, тройку (`x64-windows`) и путь к toolchain-файлу
    исполнитель сверяет с документацией vcpkg, здесь без сети не
    проверялось
  - `cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=<vcpkg.cmake> && cmake
    --build build` — покрывает только MSVC (тулчейн раннера по умолчанию);
    MinGW сознательно не входит в объём, см. «Замечания»
- [ ] Зафиксировать конкретные версии сторонних actions (`actions/checkout`
      и т. п.) — исполнитель проверяет актуальные major-версии на момент
      реализации

## Критерий готовности

- [ ] `.github/workflows/ci.yml` существует и описывает три job:
      `linux`, `macos`, `windows`
- [ ] Пробный PR с намеренно неотформатированным файлом в `src/` — job
      `linux` падает на шаге форматирования, не доходя до сборки
- [ ] Пробный PR, вносящий предупреждение компилятора в файл из `src/`
      (например, неиспользуемая переменная) — job `linux` падает на шаге
      сборки
- [ ] Чистый пуш без изменений — все три job зелёные
- [ ] `grep -rn "driver.sh smoke" .github/workflows/ci.yml` находит вызов
      только в job `linux`
- [ ] Пробный PR, ломающий один из наборов в `tests/` — job `linux`
      падает на шаге `ctest`, а не на сборке или smoke

## Замечания

Что дублируется из `.githooks/` и почему: форматирование и сборка — потому
что хуки включаются вручную и обходятся `--no-verify`, то есть для PR из
форка или для человека, который не выполнил `git config core.hooksPath
.githooks`, хуки просто не сработают. CI — единственная проверка, которую
видят все.

Что не дублируется и почему: проверка сообщения коммита (`commit-msg` →
`.claude/skills/git-commit/check-message.sh`). Это стилистическая, а не
функциональная проверка — она не ловит сломанный код. Повторная проверка
истории коммитов PR в CI хрупкая (ломается на rebase/force-push) и
бессмысленна при сквош-мерже — итоговое сообщение задаётся при мерже, а не
в отдельных коммитах ветки. Хук на `commit-msg` уже покрывает тех, кто его
включил; для остальных цена ложных срабатываний в CI выше пользы.

Юнит-тесты и smoke проверяют разное и оба обязательны в job `linux`: тесты
покрывают логику, работающую без фреймбуфера, smoke — что игра вообще
запускается и рисует.

Матч на 2 клиентах из таблицы «Каждое изменение (tier-1)»
(`requirements.md`, раздел 9) в CI не входит — мультиплеера в проекте ещё
нет (сеть — этап 7). Появится вместе с ним, дорабатывать workflow нужно
тогда же, а не сейчас.

Когда закроется `07-01-enet-build.md`, во всех трёх job понадобится
установка ENet (либо сборка `vendor/enet/` при `-DVENDOR_ENET=ON`) — этот
workflow придётся дополнить, а не переписывать заново. Рассматривался вариант включить `-Werror` глобально в `CMakeLists.txt`
вместо проверки лога в CI grep’ом — отклонён: это заодно потребовало бы
чистой сборки без предупреждений и на тир-2, а требование «без
предупреждений» в `requirements.md` привязано только к тир-1; grep,
ограниченный job `linux`, не трогает тир-2 и не меняет поведение локальной
сборки для всех остальных платформ/компиляторов.

MinGW-сборка на Windows (второй компилятор из `requirements.md`, раздел 1,
наравне с MSVC) в объём этой задачи не входит: `windows-latest` даёт MSVC
из коробки, а MSYS2/MinGW — отдельная установка со своим набором пакетов.
Если она нужна отдельным CI-шагом — это отдельная задача (например, job
`windows-mingw`), а не расширение этой.

Полный сценарий «конец этапа» из `requirements.md`, раздел 9 (матч на
4 клиентах, `--netlag 150 --netloss 5`) в CI не входит и не будет
автоматизирован этой задачей: сегодня в игре нет сети, которую можно было
бы так нагрузить, а гонять два связанных headless-процесса — отдельная
работа, которую стоит поставить рядом с задачами этапа 7, когда появится
что проверять.

Кеширование зависимостей (`actions/cache` для vcpkg/brew) в объём не
входит — ускоряет CI, но не влияет на полноту проверки; исполнитель может
добавить по вкусу.
