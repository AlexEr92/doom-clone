## Контекст

Сегодня в `CMakeLists.txt` нет ни одного упоминания `-fsanitize` (проверено
`grep -rn "sanitiz" CMakeLists.txt .githooks/ .claude/` — пусто), и класс
ошибок памяти уже реален не в теории: при переходе на 10 игроков `MAX_SPRITES`
(96) не вмещает врагов, предметы, бочки и чужих игроков — задача
`06-02-players-array.md` поднимает лимит до 192 именно поэтому. ASan поймал
бы переполнение такого массива на первом же прогоне, а не по симптомам через
несколько тиков.

Ниже — не предположения, а результат фактического прогона с этой задачей.

**Сборка.** Собрано на месте:

```
cmake -S . -B build-san -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_C_FLAGS="-fsanitize=address,undefined -fno-sanitize-recover=all -fno-omit-frame-pointer -g" \
  -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address,undefined"
cmake --build build-san
```

Собирается чисто — те же два `-Wunused-function` в `vendor/stb_image.h:1070,
1078`, что и в обычной сборке (см. `.claude/skills/run-doom-clone/SKILL.md`),
и ни одного нового предупреждения в `src/`.

**Время сборки** (однопоточно, `-j1`, чтобы изолировать эффект санитайзеров
от параллелизма; `driver.sh build` использует `-j$(nproc)` и в разы быстрее в
секундах на многоядерной машине, но соотношение между вариантами то же):

| Вариант | Время |
|---|---|
| Release без санитайзеров (сегодняшний `CMAKE_BUILD_TYPE` по умолчанию) | ~16.6 с |
| Debug без санитайзеров | ~5.7 с |
| Debug + ASan/UBSan | ~10.9 с |

Инструментирование примерно удваивает время компиляции относительно того же
уровня оптимизации (5.7 → 10.9 с), но вся санитайзерная сборка всё равно
быстрее сегодняшней Release-сборки по умолчанию — `-O0` в Debug перевешивает
цену санитайзеров. Само по себе это не повод менять `CMAKE_BUILD_TYPE` по
умолчанию.

**Прогон под `driver.sh`.** `BUILD_DIR` — существующая переменная окружения
драйвера (`.claude/skills/run-doom-clone/driver.sh:17`), и она годится без
единой правки в самом драйвере:

```
BUILD_DIR=build-san .claude/skills/run-doom-clone/driver.sh smoke
```

прошла целиком (все PASS, FPS 62–63 против обычных ~63 — заметной просадки
от инструментирования не измерено, тайминги `HOLD_MS_DEFAULT`/`0.5с` для FPS
из `SKILL.md`, «Gotchas» корректировки не потребовали) — санитайзерный
рантайм не настолько медленнее, чтобы ломать допущения драйвера о времени
кадра под Xvfb (программный рендер, без GPU).

**Утечки требуют штатного выхода, а не `pkill`.** `LeakSanitizer` (включён по
умолчанию в ASan на Linux x86-64) отчитывается только при нормальном
завершении процесса — через `atexit`-хук, который устанавливает рантайм
санитайзера. `main()` доходит до `return 0` (`main.c:239-243`, после
`assets_shutdown`/`audio_shutdown`/`engine_shutdown`) только если цикл вышел
по `eng.running = 0`; единственный путь к этому без падения — `Escape` из
`GSTATE_MENU` (`game.c:164-169`, `g->quit = 1; g->eng->running = 0;`).
`driver.sh stop` останавливает игру через `pkill -x doom-clone`
(`driver.sh:166-173`) — это `SIGTERM` без установленного в проекте
обработчика (`grep -rn "signal\|SIGTERM" src/*.c` — пусто), процесс
завершается немедленно, `atexit`-хуки не выполняются, `LeakSanitizer`
не успевает отчитаться. Проверено на практике: тот же бинарник, остановленный
через `driver.sh stop`, даёт пустой `.run/game.log`; тот же бинарник,
доведённый до `GSTATE_MENU` и там нажавший `Escape` ещё раз (сценарий ниже),
пишет в лог полный отчёт `LeakSanitizer` — см. `bug-004-audio-init-leak.md`,
куда вынесена сама находка.

Из любого достижимого игрового состояния до выхода не больше трёх нажатий
`Escape`: `PLAYING → PAUSED` (`game.c:172-175`), `PAUSED → MENU` с
`restart = 1` (`game.c:181-185`), `DEAD`/`WIN → MENU` тоже с `restart = 1`
(`game.c:193-196`, `202-205`) — и наконец `MENU → выход`
(`game.c:164-169`). Итого не более трёх `Escape` из любой точки гарантированно
доводят процесс до штатного `return 0`.

**Ложных срабатываний SDL2/SDL2_mixer не найдено.** Прогнан ручной сценарий
поверх сборки с санитайзерами: меню → игра → ходьба → повороты → выстрел
дробовиком и пистолетом → переключение оружия (`1`/`2`) → `use` (`e`) →
`mute` (`m`) → пауза → возврат в меню → выход. Единственный отчёт за весь
прогон — утечка `audio_init()` (`bug-004-audio-init-leak.md`), то есть
дефект в коде проекта, а не в SDL2/SDL2_mixer. Подавления в этой задаче не
заводятся — заводить их без воспроизведённого ложного срабатывания означало
бы гадать.

**`vendor/stb_image.h` собирается чисто, но не исполняется.** `assets_load_png()`
(`assets.c:338`) не вызывается нигде в текущем коде (`CLAUDE.md`: «exists but
is unused»), так что декодер PNG из `vendor/stb_image.h` ни разу не
отработал в этом прогоне — сборка под санитайзерами ничего не говорит о его
рантайм-поведении. Когда `feat-001-file-textures-weapon-enemy.md` подключит
реальную загрузку PNG, стоит повторить прогон на настоящем файле: у stb_image
за пределами этого проекта известны срабатывания UBSan (сдвиги, приведения
указателей) в декодере — сейчас утверждать это про версию из `vendor/` было
бы домыслом, не проверено.

**`.gitignore` не покрывает отдельный каталог сборки.** Сегодня в нём —
`/build/` и `/out/` как отдельные записи (`.gitignore:2-3`), без общего
шаблона. Каталог `build-san/`, сконфигурированный вручную для этой проверки,
остался у `git status --short` как `??` — нужна отдельная строка.

**`pre-push` не трогается.** `.githooks/pre-push` сегодня собирает `build/`
и гоняет `driver.sh smoke` при каждом push (см. сам хук, комментарий вверху:
«needs a build and an X server and takes seconds, and a slow pre-commit only
teaches people to pass --no-verify»). Санитайзерная сборка — это отдельный,
не собранный кешем каталог (`build-san`, не `build`), поэтому автоматически
никак не участвует в `pre-push`; специально включать её туда не нужно —
причина та же, что уже написана в самом хуке.

## Замечания

`lint` (`.claude/skills/lint/lint.sh`, cppcheck) и санитайзеры проверяют
разное и не заменяют друг друга: cppcheck читает текст программы и не
исполняет её — ловит то, что видно по шаблону (несовпадение типов,
очевидные null-разыменования, недостижимый код). Санитайзеры инструментируют
исполняемый код и ловят то, что происходит только во время реального
прогона — переполнение конкретного буфера при конкретных данных,
use-after-free, разыменование через несколько кадров после освобождения,
неопределённое поведение (переполнение знаковых целых, сдвиги, деление на
ноль). У них разная полнота: cppcheck проверяет весь `src/` за секунды без
запуска игры, санитайзеры — только то, что реально исполнилось за время
прогона (`driver.sh smoke` или ручной сценарий), и ничего не скажут о ветках
кода, которые не были задействованы.

CI (`chore-001-github-actions-ci.md`, ещё открыта) сегодня не существует —
подключать туда санитайзерную сборку не входит в объём этой задачи;
после `chore-001` это естественное расширение job `linux`
(дополнительный шаг: собрать `build-san` и прогнать
`BUILD_DIR=build-san driver.sh smoke` + `quit`), но правка `ci.yml` —
отдельная работа, не эта.

Раздел 1 `requirements.md` требует «без предупреждений при `-Wall -Wextra`
на tier-1» и не упоминает санитайзеры вовсе — они не входят в определение
готовности мультиплеера (раздел 10 того же документа), но прямо помогают
пункту «без падений... и утечек памяти» в его первом же критерии. `tier-2`
(macOS, Windows) эта задача не трогает: `ENABLE_SANITIZERS` — не-GNU/Clang
компилятор просто предупреждает и ничего не делает, MSVC-сборка не ломается.

LeakSanitizer по умолчанию доступен только на Linux x86-64 — на macOS
утечки ловятся иначе (инструмент `leaks`, отдельная настройка), в объём
задачи не входит: `requirements.md` требует от tier-2 только успешной
сборки, не полного набора санитайзерных проверок.
