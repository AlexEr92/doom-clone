диффов перед закрытием задачи, по образцу уже существующего
`.claude/agents/project-manager.md`
**Зависит от:** —
**Блокирует:** —
**Оценка:** новый файл, без диффа кода; по объёму сопоставим с
`.claude/agents/project-manager.md` (150 строк) — ориентировочно
120–180 строк текста инструкции
**Приоритет:** не блокирует ни один этап, но полезно завести раньше первых
диффов этапа 5 — тогда есть чем проверять сами эти диффы с самого начала

## Контекст

В `.claude/agents/` сегодня один агент — `project-manager` (`.claude/agents/
project-manager.md`), он только заводит task-файлы и ничего не проверяет.
Независимой проверки чужого диффа перед тем, как задача закрывается по
процедуре из `docs/tasks/README.md` («Как закрыть задачу»), не существует.

Проверяемость диффа сегодня опирается только на то, что исполнитель
запустит сам за собой:

- `.claude/skills/lint/lint.sh` — статический анализ cppcheck, режимы `all`
  (весь проект), `changed` (только файлы, отличающиеся от `HEAD`,
  застейдженные и незастейдженные вместе), `strict` (добавляет `style`,
  советы, не дефекты). Не хук, специально не встроен ни в какой процесс —
  `.claude/skills/lint/SKILL.md`: «meant to be run deliberately — by hand,
  or by a reviewer before a change lands»
- `ctest --test-dir build --output-on-failure` — юнит-тесты из `tests/`
  на Unity, по набору на модуль игровой логики
- `.claude/skills/run-doom-clone/driver.sh smoke` — единственная проверка,
  что игра вообще работает целиком (сборка, меню, движение, поворот,
  выстрел); юнит-тесты рендера не касаются
- `.githooks/{pre-commit,commit-msg,pre-push}` — формат (`clang-format`),
  сообщение коммита, сборка+smoke перед push. Все три включаются вручную
  (`git config core.hooksPath .githooks`) и обходятся `--no-verify`; то же
  самое отмечено в `docs/tasks/chore-001-github-actions-ci.md` как причина
  заводить CI — хуки защищают только того, кто их включил и не обошёл, а не
  дерево как таковое
- CI не существует (`docs/tasks/chore-001-github-actions-ci.md`, ещё
  открыта), `tests/` не существует (`docs/tasks/test-001-unit-test-harness.md`,
  ещё открыта; `tests/replay_test.c` из `docs/requirements.md`, раздел 9,
  тоже не существует — его вводит `06-01`)

В окружении уже есть встроенный универсальный skill `code-review`
(корректность, переиспользование, упрощение по произвольному диффу или
PR) — он ничего не знает ни про критерии приёмки конкретной task-задачи в
`docs/tasks/`, ни про `lint`/`driver.sh smoke` этого проекта, ни про
специфичные конвенции `CLAUDE.md` (changelog-free task-файлы, запрет на
хеши коммитов, именование). Агент из этой задачи — не замена ему, а
проект-специфичная надстройка поверх процесса `docs/tasks/README.md`.

## Что сделать

- [ ] Создать `.claude/agents/reviewer.md`: YAML frontmatter (`name:
      reviewer`, `description:` — триггеры вида «review a diff/change
      before it lands», «review before closing a task», «verify acceptance
      criteria», `tools: Read, Grep, Glob, Bash, Skill`, `model: sonnet`),
      далее текст инструкции на английском, тем же тоном и структурой, что
      `.claude/agents/project-manager.md` — короткие разделы, императивы,
      ссылки на конкретные пути и строки, а не общие слова. В `tools:`
      сознательно нет `Write`/`Edit`: ревьюер не правит код и не создаёт
      файлов. По той же причине он не запускает `project-manager` сам —
      заведение задачи это действие с последствиями, а роль ревьюера
      заканчивается на докладе; что делать с находкой, решает владелец
- [ ] Зафиксировать входной контракт:
  - обязательный параметр — путь/имя task-файла (`docs/tasks/*.md`, либо
    `docs/closed_tasks/*.md` для ревью постфактум) — источник секции
    «Критерий готовности»;
  - необязательный параметр — диапазон диффа; значение по умолчанию —
    незакоммиченные изменения (staged+unstaged относительно `HEAD`), тот
    же охват, что у `lint.sh changed`; вызывающий может передать явный
    диапазон коммитов или имя ветки, когда изменение уже закоммичено;
  - если задача не названа — агент не отказывает, а явно сообщает об
    ограничении и продолжает только статическим анализом, smoke и
    проверкой конвенций, не выдумывая критерии приёмки
- [ ] Описать три обязательных источника проверки и то, как агент их
      использует:
  1. **Критерии приёмки** — построчно пройтись по чеклисту «Критерий
     готовности» указанной задачи; по каждому пункту — выполнено / не
     выполнено / нельзя проверить и почему;
  2. **Статический анализ** — вызвать skill `lint`
     (`.claude/skills/lint/lint.sh changed`, gate-уровень); всё, что он
     находит на gate-уровне — дефект, поднимать в отчёте. `strict` —
     по желанию, как advisory, с оговоркой из `.claude/skills/lint/
     SKILL.md` о том, что не каждая находка `style` стоит того, чтобы её
     брать;
  3. **Работоспособность** — вызвать skill `run-doom-clone`
     (`driver.sh smoke`) для диффов, трогающих `src/`; для диффов только в
     `docs/`/`.claude/` — пропустить с явной пометкой причины, а не молчать
- [ ] Описать проверку конвенций `CLAUDE.md`, которые не проверяются
      механически:
  - task/plan-файлы — спецификация, а не хроника: нет секции с историей
    правок, нет фраз вида «раньше было N, теперь 10», нет следов диалога;
  - нигде в диффе (ни в коде, ни в документации) нет ссылок на хеш
    коммита — ориентироваться на эвристику `.claude/skills/git-commit/
    check-message.sh` (голое hex-слово 7–40 символов вне `0x`-литералов),
    не считать её единственным механическим тестом;
  - в дифф не затесался фикс постороннего бага мимо предмета задачи —
    сверить список тронутых файлов/мест с секцией «Затрагиваемые файлы» и
    «Что сделать» задачи; расхождение — пункт отчёта, а не повод
    останавливать проверку;
  - именование по таблице из `CLAUDE.md` (`snake_case` для функций,
    `CamelCase` для структур/enum-типов, `snake_case` для полей,
    `SCREAMING_SNAKE` с общим префиксом для enum-констант, `<PREFIX>_COUNT`
    сентинелом последним);
  - формат — `clang-format --dry-run -Werror` по изменённым `.c/.h` (то же,
    что делает `.githooks/pre-commit`, но безусловно и по всему диффу, а не
    только по застейдженной части);
  - если дифф содержит коммиты — сообщение проверяется
    `.claude/skills/git-commit/check-message.sh --history N` (50/72,
    тип-префикс, без `Co-Authored-By`, без хеша)
- [ ] Описать разбор диффа тестов отдельно от их прогона:
  - агент прогоняет `ctest --test-dir build --output-on-failure` сам, не
    доверяя чужому прогону — повторный прогон нужен из-за возможного
    грязного дерева или устаревшей сборки у исполнителя;
  - отдельно, текстом, разбирает дифф файлов `tests/*` по трём вопросам:
    появились ли тесты на само изменение; проверяют ли они наблюдаемое
    поведение (намерение) или повторяют реализацию; не ослаблен ли и не
    удалён ли существующий тест, чтобы изменение прошло — это вопрос к
    содержанию диффа, а не к коду выхода `ctest`;
  - задачи этапов 5–6 меняют сигнатуры, на которые опираются тесты, и правка
    соответствующего `tests/test_*.c` входит в их объём — отсутствие такой
    правки там, где сигнатура изменилась, пункт отчёта, а не мелочь
- [ ] Зафиксировать формат отчёта: связный текст в ответе агента (файлов на
      диск агент не пишет), с разделами «Критерии приёмки», «Статический
      анализ», «Работоспособность», «Конвенции», «Тесты» — по каждому либо
      результат с конкретными путями/строками, либо явный no-op с причиной.
      Без итогового вердикта «принято»/«не принято» по задаче в целом —
      решение остаётся за владельцем
- [ ] Зафиксировать передачу находок в `project-manager`: ревьюер не
      вызывает его сам (см. выше — заведение задачи вне его роли),
      поэтому находки, достойные отдельной `bug-*`/`chore-*`/
      `feat-*`-задачи, формулирует в отчёте так, чтобы их можно было
      передать `project-manager` без повторного расследования — причина, а
      не симптом, конкретное место в коде, шаги воспроизведения для
      дефектов (по аналогии с п. 4 инструкции `project-manager`,
      `.claude/agents/project-manager.md:44-47`). Кто и когда вызывает
      `project-manager` с этим текстом — решает вызывающий (человек или
      родительская сессия), не сам ревьюер
- [ ] Явно перечислить, чего агент не делает: не пишет и не редактирует
      файлы, не коммитит, не двигает task-файлы в `docs/closed_tasks/`, не
      выносит блокирующего вердикта — только отчёт

## Замечания

Роль задана целиком снаружи этой задачи (не предмет решения исполнителя):
агент докладывает, а не блокирует; не чинит найденное; проверяет три
источника (критерии приёмки, `lint`, `driver.sh smoke`); сверяет
немеханические конвенции `CLAUDE.md`; тесты прогоняет сам и отдельно
разбирает их дифф по трём вопросам. Решения, которые пришлось принять при
постановке этой задачи — входной контракт, формат отчёта, способ передачи
находок в `project-manager` — описаны в «Что сделать» выше и не подлежат
пересмотру исполнителем без явной причины.

Почему ревьюер не заводит задачи сам: его роль заканчивается на докладе,
решение принимает владелец. Дай он себе право создавать `bug-*`-файлы — и
он перестанет быть проверяющим, став вторым исполнителем, а поток задач
начнёт пополняться находками, которые никто не подтвердил.

Когда закроется `docs/tasks/chore-001-github-actions-ci.md`, CI начнёт
гонять `lint`/сборку/smoke автоматически при каждом пуше — `reviewer`
всё равно не дублируется с ним: CI даёт только код возврата по трём
проверкам, а критерии приёмки конкретной задачи, соответствие диффа её
объёму и немеханические конвенции `CLAUDE.md` требуют чтения и суждения,
которые CI не производит.

Не входит в объём: встраивание `reviewer` в `.githooks/` или в CI —
сегодня он запускается вручную (или вызывающей сессией) по явному
запросу; автоматический вызов на каждый пуш/PR, если понадобится —
отдельная задача после того, как появится сам CI.
