# 06-01 — `world.c/.h` и единый `world_step()`

**Этап:** 6 — Мультиплеерная логика локально
**Зависит от:** 05-05
**Блокирует:** 06-02, 06-06, 07-04, 08-02
**Оценка:** ~150 строк изменений

## Контекст

`World` объявлен прямо в `main.c:20-30`, а тик симуляции размазан по циклу
`main.c:156-172` вперемешку с рендером, FSM и обработкой событий SDL.

Для сети нужна ровно одна функция тика, которую вызывают и сервер, и клиент
при предсказании. Если сервер и клиент считают разным кодом — предсказание
разойдётся гарантированно.

## Что сделать

- [ ] Создать `src/config.h` — единственный источник истины для лимитов и
      настраиваемых констант: `MAX_PLAYERS`, `MAX_ENEMIES`, `MAX_ITEMS`,
      `MAX_DOORS`, `MAX_SPRITES`, `MAX_SPAWNS`, `MAX_EVENTS`, тикрейт,
      частота снапшотов, порт, тайминги респавна. Значения обязаны
      соответствовать [requirements.md](../requirements.md), раздел 5.
      Лимиты, разбросанные сейчас по `sprite.h:27`, `enemy.h:38`,
      `item.h:25`, `door.h:22`, — перенести сюда
- [ ] Создать `src/world.h`, перенести туда `World` из `main.c:20-30`,
      добавить `EventQueue events` (из 05-05) и `uint32_t tick`
- [ ] Перенести `world_load()` (`main.c:32-70`) в `world.c`
- [ ] Собрать тик в одну функцию:
  ```c
  void world_step(World *w, const PlayerInput inputs[], int count, double dt);
  ```
      Внутри — в том же порядке, что сейчас в `main.c:159-169`:
      движение игроков → двери (use + update) → ИИ врагов → предметы →
      оружие (update + fire). Порядок фиксируем: от него зависит
      воспроизводимость при реконсиляции.
- [ ] `world_step()` в начале очищает `w->events`, в конце инкрементирует
      `w->tick`
- [ ] `PlayerInput` объявить в `input.h` (сетевой формат — в 07-03):
  ```c
  typedef struct { uint32_t tick; uint16_t buttons; float angle; } PlayerInput;
  ```
- [ ] `main.c` — цикл фикс-шага сводится к
      `world_step(&world, inputs, n, FIXED_DT)`; рендер, FSM и SDL остаются
      снаружи
- [ ] Добавить `src/world.c` в `CMakeLists.txt:25-42`

- [ ] `main.c` сократился примерно вдвое; в фикс-шаге ровно один вызов

## Замечания

Тест на воспроизводимость из последнего пункта оформить как
`tests/replay_test.c` — он обязателен по
[requirements.md](../requirements.md), раздел 9, и является единственной
автоматической защитой от рассинхрона предсказания. Ловит скрытые
зависимости от времени, от `rand()` и от несброшенного состояния;
понадобится снова на этапе 8. Подключается функцией `doom_test()` из
`tests/CMakeLists.txt` — тем же механизмом `add_test()`/CTest, что и
остальные наборы, а не отдельным раннером.

Лимиты, переезжающие в `config.h`, тесты берут из заголовков (`MAX_SPRITES`
в `tests/test_enemy.c`, `MAX_DOORS`, `MAX_ITEMS`) — после переноса они
должны продолжать разрешаться.

`config.h` не должен включать SDL и другие заголовки — только `#define`
и `static_assert`. Иначе он потянет зависимости в headless-сервер.
