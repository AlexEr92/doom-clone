# 07-04 — Сервер: тик, приём ввода, рассылка снапшотов

**Этап:** 7 — Сеть: транспорт, протокол, снапшоты
**Зависит от:** 07-02, 07-03, 06-06
**Блокирует:** 07-05
**Оценка:** ~280 строк нового кода (накопитель событий — ещё ~30: структура, добавление после тика, сброс после отправки; оценка по размеру `EventQueue` в `event.h`, а не по готовому коду)

## Контекст

Сервер — источник истины: гоняет `world_step()` (06-01) на 60 Гц, применяя
последний полученный ввод каждого клиента, и рассылает снапшоты на 20 Гц.
Клиенты ничего не решают сами (кроме собственного угла поворота, см. 06-06).

## Что сделать

- [ ] `src/net_server.h`:
  ```c
  typedef struct Server Server;
  Server *server_create(uint16_t port, const char *map_path);
  void    server_destroy(Server *s);
  void    server_tick(Server *s, double dt);   /* вызывать из фикс-шага */
  int     server_local_player(const Server *s); /* для listen-server */
  World  *server_world(Server *s);
  ```
- [ ] Состояние клиента на сервере:
  ```c
  typedef struct {
      int used; NetPeerId peer; uint8_t player_id;
      PlayerInput last_input; uint32_t last_input_tick;
      float time_since_input;
  } ServerClient;
  ```
- [ ] Обработка событий транспорта:
  - `NET_EV_CONNECT` → ждём `MSG_JOIN`
  - `MSG_JOIN` → проверка `proto == PROTO_VERSION` и наличия слота →
    `world_add_player()` → `MSG_ACCEPT{your_id, seed, map}`; иначе `MSG_REJECT`
    и `net_disconnect()`: уже отправленный `MSG_REJECT` он доставит до
    разрыва, а `NET_EV_DISCONNECT` по этому пиру больше не придёт. Хост
    создаётся `net_host_server(port, NET_MAX_PEERS)` — место сверх
    `MAX_PLAYERS` нужно, чтобы отклоняемый клиент успел подключиться
  - `MSG_INPUT` → сохранить, если `tick` новее сохранённого (пакеты UDP
    приходят с перестановками — старые отбрасывать)
  - `NET_EV_DISCONNECT` → `world_remove_player()`
- [ ] Тик: собрать `PlayerInput[]` из `last_input` всех клиентов →
      `world_step()`. Клиент без свежего ввода (>0.2 с) считается стоящим:
      кнопки обнуляются, угол сохраняется
- [ ] Рассылка снапшотов: аккумулятор на 1/20 с, `snapshot_write()` →
      `snapshot_encode()` → `net_broadcast(..., channel 1, reliable=0)`
      с тем числом байт, что вернул `snapshot_encode()`: на провод идут
      списки, обрезанные по счётчикам, а не `MsgSnapshot` целиком.
      В `last_input_tick` каждому клиенту — **его** номер (значит,
      персональная отправка, а не broadcast; либо broadcast + поле на каждого
      игрока в `NetPlayer.flags`)
- [ ] Накопление событий между снапшотами. `world_step()` первым делом
      очищает `World.events` (`world.c`), поэтому там остаются события
      только последнего тика, а снапшот уходит раз в три тика
      (`TICK_RATE` / `SNAPSHOT_RATE` = 60 / 20). Без накопителя события двух
      тиков из трёх до клиентов не доходят, то есть ~2/3 звуков теряются
      даже при нулевой потере пакетов. Сервер держит буфер вне `World` —
      поле `Server` типа `EventQueue` или аналога большей ёмкости — и после
      каждого `world_step()` дописывает в него `w->events`. Ёмкость —
      `ceil(TICK_RATE / snaprate) * MAX_EVENTS`, считать от самой низкой
      допустимой частоты снапшотов (см. `--snaprate` в замечаниях), а не от
      20 Гц. При переполнении новые события отбрасываются, как в
      `event_push()`: потеря звука не влияет на симуляцию. После отправки
      снапшотов буфер обнуляется
- [ ] Запись событий в снапшот идёт из накопителя, а не из `w->events`:
      после `snapshot_write()` сервер заменяет `events`/`event_count`
      результатом отбора и схлопывания из 07-06 над накопленным списком
      (для каждого клиента отдельно, из одного общего буфера)
- [ ] `srand(seed)` из `MSG_ACCEPT` — разброс дробовика (`weapon.c:84`)
      крутит **только сервер**
- [ ] Listen-server: локальный игрок добавляется без сети, его ввод
      кладётся в тот же массив

## Затрагиваемые файлы

`net_server.c/.h` (новые), `main.c`, `CMakeLists.txt`

## Критерий готовности

- [ ] Сервер стартует, принимает 10 подключений, отклоняет 11-е
      (`MAX_PLAYERS 10`) с внятным `MSG_REJECT`
- [ ] Клиент с чужим `PROTO_VERSION` отклоняется
- [ ] Убитый клиент исчезает из мира в пределах таймаута, слот
      переиспользуется новым подключением
- [ ] Сервер держит стабильные 60 тиков/с при 10 клиентах
- [ ] Исходящий трафик при 10 клиентах в DM ≈ 80 КБ/с, в co-op ≈ 200 КБ/с
- [ ] Потеря ввода на один тик не приводит к телепорту игрока
- [ ] Выстрел, сделанный в тик, который не совпал с отправкой снапшота,
      слышен у клиента: тест на сервере без сокетов или с loopback —
      три `world_step()` подряд, выстрел во втором, один снапшот после
      третьего; в нём есть `EV_SHOT`. Тот же тест для события в первом тике
- [ ] После отправки снапшотов накопитель пуст: событие не приходит
      клиенту дважды

## Замечания

`last_input_tick` персонален для каждого клиента, поэтому честный broadcast
одного буфера не проходит. Проще всего слать каждому свой снапшот — при 10
игроках это 200 отправок в секунду и ~200 КБ/с исходящего в co-op.
Для LAN-сервера это незаметно, но на домашнем аплинке 200 КБ/с (1.6 Мбит/с)
уже ощутимо — стоит вынести частоту снапшотов в параметр запуска
(`--snaprate`), чтобы можно было опустить до 15 Гц.

Накопитель событий принадлежит серверу, а не `World`: `world_step()`
обязан по-прежнему очищать `events` в начале тика — на этом держатся
`tests/replay_test.c` и клиентское предсказание, где `events` — события
одного тика. Листен-сервер: локальный игрок, как и раньше, разбирает
`w->events` после каждого тика, накопитель ему не нужен.

Отбрасывание вводов «не новее сохранённого» обязательно: UDP переставляет
пакеты, и применение устаревшего ввода даст рывок назад.
