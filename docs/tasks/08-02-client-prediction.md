# 08-02 — Предсказание своего игрока

**Этап:** 8 — Качество netcode
**Зависит от:** 07-05, 06-01, 06-06
**Блокирует:** 08-03
**Оценка:** ~150 строк нового кода

## Контекст

Сейчас клиент ждёт подтверждения сервера, чтобы сдвинуть своего игрока —
на RTT 50 мс это ощущается как «залипание» управления, на 150 мс играть
невозможно.

Решение: клиент применяет свой ввод локально сразу, тем же `world_step()`
(06-01), и запоминает неподтверждённые вводы. Сходимость с сервером —
задача 08-03.

## Что сделать

- [ ] Кольцевой буфер вводов:
  ```c
  #define INPUT_HISTORY 128   /* ~2 с при 60 Гц */
  typedef struct {
      PlayerInput inputs[INPUT_HISTORY];
      int head, count;
  } InputHistory;
  ```
- [ ] Каждый тик: отправить `MSG_INPUT`, положить в историю и **сразу**
      применить локально через `world_step()` по локальному `World`
- [ ] Локального игрока исключить из `snapshot_apply()` — иначе снапшот
      будет затирать предсказанную позицию и вернётся дёрганье
- [ ] Изолировать предсказание от чужих сущностей: предсказывается **только**
      движение своего игрока и его коллизии с картой. Врагов, двери и
      чужих игроков предсказывать не пытаемся — берём из снапшота
- [ ] Стрельба не предсказывается: локально проигрывается только анимация
      отдачи и звук, урон приходит от сервера. Иначе будут «фантомные»
      попадания
- [ ] Расход патронов предсказывать можно (мгновенная обратная связь в HUD),
      но при расхождении — сервер прав

## Затрагиваемые файлы

`net_client.c/.h`, `world.c`, `main.c`

## Критерий готовности

- [ ] Управление отзывчиво при искусственных 150 мс задержки
- [ ] Стена останавливает игрока мгновенно, без «продавливания» и отката
- [ ] Локальная позиция при RTT ≈ 0 совпадает с серверной с точностью
      до float-погрешности (это база для 08-03)
- [ ] Отладочный вывод расхождения предсказания (полноценный оверлей — 08-04)
- [ ] Предмет, который снапшот показал подобранным, не возвращается на
      клиенте раньше, чем на сервере (см. замечания про `item_update()`)

## Замечания

Ключевое условие корректности: клиент и сервер обязаны выполнять **ровно
ту же** функцию `world_step()`. Любая ветка вида «на клиенте пропустим ИИ»
внутри неё создаёт расхождение, которое проявится не сразу и будет искаться
долго. Разделение делается снаружи — тем, какие части результата клиент
оставляет себе.

`rand()` — источник расхождения по определению. Именно поэтому стрельба
(с разбросом дробовика, `weapon.c:95`) не предсказывается.

Оружие своего игрока приходит в каждом снапшоте целиком: блок
`MsgSnapshot.yours` (`net_protocol.h`) несёт маску подобранных стволов и
патроны всех пяти, и `snapshot_apply()` кладёт их в игрока `yours.id`.
О чужих игроках снапшот несёт только ствол в руках. Полный набор на каждого
из десяти игроков для каждого из десяти получателей поднял бы исходящий
трафик сервера в deathmatch примерно на четверть (около 95 КБ/с вместо 75),
а нужен он клиенту только для своего игрока. Поэтому, исключая
локального игрока из `snapshot_apply()`, предсказание отделяет позицию от
инвентаря: позиция предсказывается, а `owned` и патроны из `yours` клиент
принимает от сервера. Иначе подобранный ствол на клиенте не появится, а
`weapon_switch()` откажется на него переключать.

`world_step()` на клиенте вызывает и `item_update()` (`world.c`), а тот
возвращает подобранный предмет по таймеру `Item.respawn_timer`
(`ITEM_RESPAWN_TIME`, 30 с). Снапшот таймер не несёт: `snapshot_apply()`
(`net_protocol.c`) выставляет предметам только `active` из маски
`items_alive`. У предмета, который снапшот показал подобранным, на клиенте
`respawn_timer == 0`, и первый же предсказанный тик вернёт его на место, а
если свой игрок стоит рядом — ещё и «подберёт» заново, подмешав патроны и
событие в предсказанное состояние. Предметы, как и двери с врагами, из
предсказания исключаются, и решить надо до первой строки кода одним из
двух способов: либо клиент после каждого предсказанного тика (или вместо
`item_update()` внутри предсказания, снаружи `world_step()`, не ветвясь в
нём) заново накладывает `items_alive` из последнего снапшота, либо
снапшот начинает нести время до возврата предмета. Второй путь меняет
формат сообщения и бюджет трафика, поэтому первый предпочтительнее; в обоих
случаях в критерии готовности нужна проверка: предмет, подобранный
другим игроком, за 30 с предсказания у клиента не появляется раньше, чем
у сервера.
