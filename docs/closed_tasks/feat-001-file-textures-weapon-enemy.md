## Контекст

Вся графика в игре генерируется процедурно в `assets.c`: `gen_brick()`,
`gen_weapon()`, `gen_enemy()` и так далее заполняют `Texture.pixels`
пиксель за пикселем. Единственный внешний ассет — файл карты
(`assets/maps/level1.txt`).

Загрузчик PNG уже написан и не используется:

```c
int assets_load_png(Texture *tex, const char *path);   /* assets.h:33 */
```

Реализация в `assets.c:338-362` читает файл через `stbi_load()`
(`vendor/stb_image.h`, собран с `STBI_ONLY_PNG`) и упаковывает пиксели в
том же порядке байт, что и `make_color()` (`utils.h:48-51`) — код уже
согласован с форматом текстуры `SDL_PIXELFORMAT_ABGR8888`, ничего
пересчитывать не нужно. Проблема ровно одна: `assets_init()`
(`assets.c:364-394`) никогда его не вызывает.

Рендер уже не завязан на фиксированный размер текстуры:

- `sample_nearest()` (`raycast.c:8-23`) и текстурирование стен
  (`raycast.c:134-142`) берут `tex->w`/`tex->h`, а не константу
  `TEX_SIZE`
- `sprite_render()` (`sprite.c:122-142`) вычисляет ширину спрайта из
  `spriteHeight * texW / texH`, то есть сохраняет пропорции исходной
  картинки любого размера
- `hud_draw_weapon()` (`hud.c:69-113`) масштабирует оружие по высоте
  экрана (`target_h = SCREEN_H * 0.40`) и берёт ширину из
  `base->w`/`base->h`

Значит менять рендер не требуется — только подключить уже написанный
загрузчик и описать, что именно и куда класть.

Прозрачность в этом рендере **бинарная**, без блендинга: и
`sprite_render()` (`sprite.c:180-182`), и `hud_draw_weapon()`
(`hud.c:106-109`) пропускают пиксель только при `(c & 0xFF000000u) == 0`
(альфа строго 0), а любой другой альфа-байт рисуется как непрозрачный —
полупрозрачные/сглаженные края у PNG превратятся в сплошную кайму того
цвета, что был под сглаживанием.

Бэклоговая формулировка ограничивает объём словами «оружия и врагов» —
это ровно 5 полей `Assets` (`assets.h:13-27`):

| Поле `Assets` | Генератор сегодня |
|---|---|
| `weapon_pistol` | `gen_weapon()` (`assets.c:272-305`) |
| `weapon_shotgun` | `gen_weapon_shotgun()` (`assets.c:307-336`) |
| `sprite_enemy` | `gen_enemy()` (`assets.c:139-164`) |
| `sprite_enemy_serg` | `gen_enemy_serg()` (`assets.c:166-191`) |
| `sprite_enemy_dead` | `gen_enemy_dead()` (`assets.c:193-211`) |

Стены/пол/потолок (`wall_brick`, `wall_door`, `floor_tex`,
`ceiling_tex`) и подбираемые предметы (`sprite_barrel`, `sprite_medkit`,
`sprite_ammo`, `sprite_armor`) в задачу не входят и остаются
процедурными.

**Владелец проекта сам рисует и предоставляет PNG-файлы. Исполнитель
задачи графику не создаёт** — результат задачи это (а) механизм
подстановки файла вместо процедурной текстуры и (б) точная раскладка
файлов ниже, по которой владелец сможет положить готовые файлы без
дополнительных вопросов.

## Ожидаемая раскладка файлов

Новый каталог `assets/textures/` (рядом с `assets/maps/`), пути —
относительно корня проекта, как и у карты (`main.c:82`,
`"assets/maps/level1.txt"`):

| Файл | Размер | Формат | Прозрачность |
|---|---|---|---|
| `assets/textures/weapon_pistol.png` | 128×128 | PNG, RGBA | alpha=0 вне силуэта оружия/рук |
| `assets/textures/weapon_shotgun.png` | 128×128 | PNG, RGBA | alpha=0 вне силуэта оружия/рук |
| `assets/textures/sprite_enemy.png` | 64×64 | PNG, RGBA | alpha=0 вне силуэта персонажа |
| `assets/textures/sprite_enemy_serg.png` | 64×64 | PNG, RGBA | alpha=0 вне силуэта персонажа |
| `assets/textures/sprite_enemy_dead.png` | 64×64 | PNG, RGBA | alpha=0 вне силуэта трупа |

Размеры взяты из сегодняшних процедурных заглушек (`TEX_SIZE=64` для
спрайтов, 128×128 захардкожено в `gen_weapon()`/`gen_weapon_shotgun()`)
и это рекомендация, а не ограничение кода: загрузчик и рендер, как
показано выше, принимают PNG любого размера. Отступление от размера не
ломает игру, но меняет пропорции — например, не квадратный
`sprite_enemy.png` растянется по ширине относительно масштабов,
подобранных в `sprite_add()` (`sprite.c:12-28`).

Прозрачность должна быть жёсткой (0 или 255), без сглаживания по
альфа-каналу — рендер не блендит полутона (см. «Контекст»).

## Что сделать

- [ ] Создать каталог `assets/textures/` (пустой, файлы кладёт владелец
      отдельно от этой задачи)
- [ ] В `assets.c` добавить статический хелпер, например:
      ```c
      static void load_texture_override(Texture *slot, const char *path)
      {
          FILE *f = fopen(path, "rb");
          if (!f) {
              return; /* файла нет — ожидаемое состояние по умолчанию,
                          оставляем процедурную текстуру молча */
          }
          fclose(f);
          Texture tmp;
          if (assets_load_png(&tmp, path) == 0) {
              texture_free(slot);
              *slot = tmp;
              printf("assets: loaded %s\n", path);
          }
          /* иначе assets_load_png() уже вывел причину ошибки в stderr —
             слот остаётся процедурным */
      }
      ```
      Проверка `fopen` до вызова `assets_load_png()` нужна, чтобы
      обычный случай «файла ещё нет» не печатал `fprintf(stderr, ...)`
      из `assets_load_png()` (`assets.c:343`) при каждом запуске —
      предупреждение должно оставаться только для реально битого файла
- [ ] Вызвать `load_texture_override()` в `assets_init()` сразу после
      соответствующего `gen_*()`, для всех 5 полей из таблицы выше
- [ ] Сигнатуру `assets_init(Assets *a)` не менять — путь к каталогу
      зашит как литерал `"assets/textures/..."`, по аналогии с
      `map_path` в `main.c:82`

## Критерий готовности

- [ ] `grep -n "assets_load_png" src/assets.c` показывает вызов из
      `assets_init()`, а не только определение функции
- [ ] Каталог `assets/textures/` пуст или отсутствует — игра выглядит
      как сегодня, `.claude/skills/run-doom-clone/driver.sh smoke`
      проходит
- [ ] Один тестовый PNG (например, залитый одним цветом с прозрачным
      краем) кладётся как `assets/textures/weapon_pistol.png`, остальные
      4 файла отсутствуют — при старте в stdout/stderr видно сообщение о
      загрузке именно этого файла, оружие в HUD визуально отличается от
      процедурного, враги и второй ствол не меняются;
      `driver.sh smoke` проходит
- [ ] Файл по тому же пути с мусорным содержимым (не PNG) не приводит к
      падению `assets_init()`: слот остаётся процедурным, в stderr
      попадает предупреждение из `assets_load_png()`
- [ ] Ни один файл вне пяти полей из таблицы (стены, пол, потолок,
      бочка, аптечка, патроны, броня) не тронут

## Замечания

Объём заведомо мал, потому что рендер уже не завязан на фиксированный
размер текстуры (см. «Контекст») — вся работа это подключение уже
написанного `assets_load_png()`, а не переписывание сэмплинга.

Тестовый PNG для проверки критериев не обязательно коммитить в
репозиторий — финальную графику отдельно предоставляет владелец
проекта по таблице выше.

Будет ли готовая графика в итоге закоммичена в репозиторий или храниться
вне git — решает владелец проекта; карта (`assets/maps/level1.txt`)
сегодня закоммичена, но бинарные PNG — не то же самое по весу, это не
входит в объём задачи.

Задача 06-05 (`06-05-sprites-client-side.md`) позже добавит ещё одну
процедурную текстуру — `gen_player()` для `SPRITE_PLAYER`. Она не
пересекается с этой задачей, но подстановку файла для неё, если
понадобится, естественно делать по тому же образцу
(`load_texture_override()`).
