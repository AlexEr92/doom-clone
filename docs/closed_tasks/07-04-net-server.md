# 07-04 — Сервер: тик, приём ввода, рассылка снапшотов

**Этап:** 7 — Сеть: транспорт, протокол, снапшоты
**Зависит от:** 07-02, 07-03, 06-06
**Блокирует:** 07-05
**Оценка:** ~280 строк нового кода (накопитель событий — ещё ~30: структура, добавление после тика, сброс после отправки; оценка по размеру `EventQueue` в `event.h`, а не по готовому коду)

## Контекст

Сервер — источник истины: гоняет `world_step()` (06-01) на 60 Гц, применяя
последний полученный ввод каждого клиента, и рассылает снапшоты на 20 Гц.
Клиенты ничего не решают сами (кроме собственного угла поворота, см. 06-06).

## Что сделать

- [ ] `src/net_server.h`:
  ```c
  typedef struct Server Server;
  Server *server_create(uint16_t port, const char *map_path);
  void    server_destroy(Server *s);
  void    server_tick(Server *s, double dt);   /* вызывать из фикс-шага */
  int     server_local_player(const Server *s); /* для listen-server */
  World  *server_world(Server *s);
  ```
- [ ] Состояние клиента на сервере:
  ```c
  typedef struct {
      int used; NetPeerId peer; uint8_t player_id;
      PlayerInput last_input; uint32_t last_input_tick;
      float time_since_input;
  } ServerClient;
  ```
- [ ] Обработка событий транспорта:
  - `NET_EV_CONNECT` → ждём `MSG_JOIN`
  - `MSG_JOIN` → проверка `proto == PROTO_VERSION` и наличия слота →
    `world_add_player()` → `MSG_ACCEPT{your_id, seed, map}`; иначе `MSG_REJECT`
    и `net_disconnect()`: уже отправленный `MSG_REJECT` он доставит до
    разрыва, а `NET_EV_DISCONNECT` по этому пиру больше не придёт. Хост
    создаётся `net_host_server(port, NET_MAX_PEERS)` — место сверх
    `MAX_PLAYERS` нужно, чтобы отклоняемый клиент успел подключиться
  - `MSG_INPUT` → сохранить, если `tick` новее сохранённого (пакеты UDP
    приходят с перестановками — старые отбрасывать)
  - `NET_EV_DISCONNECT` → `world_remove_player()`
- [ ] Тик: собрать `PlayerInput[]` из `last_input` всех клиентов →
      `world_step()`. Клиент без свежего ввода (>0.2 с) считается стоящим:
      кнопки обнуляются, угол сохраняется
- [ ] Рассылка снапшотов: аккумулятор на 1/20 с, `snapshot_write()` →
      `snapshot_encode()` → `net_broadcast(..., channel 1, reliable=0)`
      с тем числом байт, что вернул `snapshot_encode()`: на провод идут
      списки, обрезанные по счётчикам, а не `MsgSnapshot` целиком.
      В `last_input_tick` каждому клиенту — **его** номер (значит,
      персональная отправка, а не broadcast; либо broadcast + поле на каждого
      игрока в `NetPlayer.flags`)
- [ ] Накопление событий между снапшотами. `world_step()` первым делом
      очищает `World.events` (`world.c`), поэтому там остаются события
      только последнего тика, а снапшот уходит раз в три тика
      (`TICK_RATE` / `SNAPSHOT_RATE` = 60 / 20). Без накопителя события двух
      тиков из трёх до клиентов не доходят, то есть ~2/3 звуков теряются
      даже при нулевой потере пакетов. Сервер держит буфер вне `World` —
      поле `Server` типа `EventQueue` или аналога большей ёмкости — и после
      каждого `world_step()` дописывает в него `w->events`. Ёмкость —
      `ceil(TICK_RATE / snaprate) * MAX_EVENTS`, считать от самой низкой
      допустимой частоты снапшотов (см. `--snaprate` в замечаниях), а не от
      20 Гц. При переполнении новые события отбрасываются, как в
      `event_push()`: потеря звука не влияет на симуляцию. После отправки
      снапшотов буфер обнуляется
- [ ] Запись событий в снапшот идёт из накопителя, а не из `w->events`:
      после `snapshot_write()` сервер заменяет `events`/`event_count`
      результатом отбора и схлопывания из 07-06 над накопленным списком
      (для каждого клиента отдельно, из одного общего буфера)
- [ ] `srand(seed)` из `MSG_ACCEPT` — разброс дробовика (`weapon.c:84`)
      крутит **только сервер**
- [ ] Listen-server: локальный игрок добавляется без сети, его ввод
      кладётся в тот же массив

## Затрагиваемые файлы

`net_server.c/.h` (новые), `main.c`, `CMakeLists.txt`

## Критерий готовности

- [ ] Сервер стартует, принимает 10 подключений, отклоняет 11-е
      (`MAX_PLAYERS 10`) с внятным `MSG_REJECT`
- [ ] Клиент с чужим `PROTO_VERSION` отклоняется
- [ ] Убитый клиент исчезает из мира в пределах таймаута, слот
      переиспользуется новым подключением
- [ ] Сервер держит стабильные 60 тиков/с при 10 клиентах
- [ ] Исходящий трафик при 10 клиентах в DM ≈ 80 КБ/с, в co-op ≈ 200 КБ/с
- [ ] Потеря ввода на один тик не приводит к телепорту игрока
- [ ] Выстрел, сделанный в тик, который не совпал с отправкой снапшота,
      слышен у клиента: тест на сервере без сокетов или с loopback —
      три `world_step()` подряд, выстрел во втором, один снапшот после
      третьего; в нём есть `EV_SHOT`. Тот же тест для события в первом тике
- [ ] После отправки снапшотов накопитель пуст: событие не приходит
      клиенту дважды

## Замечания

`last_input_tick` персонален для каждого клиента, поэтому честный broadcast
одного буфера не проходит. Проще всего слать каждому свой снапшот — при 10
игроках это 200 отправок в секунду и ~200 КБ/с исходящего в co-op.
Для LAN-сервера это незаметно, но на домашнем аплинке 200 КБ/с (1.6 Мбит/с)
уже ощутимо — стоит вынести частоту снапшотов в параметр запуска
(`--snaprate`), чтобы можно было опустить до 15 Гц.

Накопитель событий принадлежит серверу, а не `World`: `world_step()`
обязан по-прежнему очищать `events` в начале тика — на этом держатся
`tests/replay_test.c` и клиентское предсказание, где `events` — события
одного тика. Листен-сервер: локальный игрок, как и раньше, разбирает
`w->events` после каждого тика, накопитель ему не нужен.

Отбрасывание вводов «не новее сохранённого» обязательно: UDP переставляет
пакеты, и применение устаревшего ввода даст рывок назад.

## Закрыто

2026-10-17 — авторитетный сервер — `src/net_server.c/.h`. Он принимает
подключения через `net_transport`, отвечает на `MSG_JOIN` сообщением
`MSG_ACCEPT` или `MSG_REJECT`, на каждый `server_tick()` прогоняет один
`world_step()` по последнему вводу каждого клиента и рассылает снапшоты.
Модуль собирается только при `ENABLE_MULTIPLAYER` и, как и протокол, стоит в
списке `NOSDL=` в `lint.sh`: SDL ему не нужен.

С «Что сделать» реализация расходится в следующем:

- **Одиночные нажатия** — по решению пользователя. Если хранить только самый
  свежий ввод и повторять его, когда нового нет, нажатие `E` или клик
  теряются, когда два ввода приходят в один тик. А когда не приходит ни
  одного, нажатие срабатывает дважды: дверь открывается и тут же
  закрывается. Поэтому выстрел, `E` и смена оружия (`BTN_ONCE`) из всех
  принятых с прошлого тика вводов складываются в ближайший тик. Повтор
  опоздавшего ввода несёт только удерживаемое (`BTN_HELD`): ходьбу и зажатый
  курок. Ввод старее сохранённого по-прежнему отбрасывается.
- **API.** `server_tick(s, local, dt)` получает ввод локального игрока, на
  выделенном сервере — `NULL`, как `GameSession.tick` в 07-07. Добавлены
  `server_add_local_player()` и `server_set_snapshot_rate()`; вторая держит
  частоту в пределах от `SNAPSHOT_RATE_MIN` (15) до `TICK_RATE`.
  `ServerClient` индексируется номером пира.
- **`main.c` не тронут.** Запустить сервер из игры можно только с флагами и
  `GameSession` из 07-07, а без них одиночная игра открывала бы сокет. Туда
  же добавлен флаг `--snaprate`.
- **Отбор событий.** Пока нет 07-06, каждый клиент получает одни и те же
  первые `MAX_EVENTS` накопленных событий, по порядку. Для этого в протокол
  добавлена `snapshot_set_events()`, через неё же пишет события
  `snapshot_write()`.
- **`config.h`**: `SNAPSHOT_RATE_MIN 15` (накопитель — ceil(60/15) × 32 =
  128 событий) и `NET_INPUT_TIMEOUT 0.2f`. В requirements.md, N10, указаны
  границы: от 15 до 60 Гц.

Сверх задачи:

- ввод с углом по модулю больше 2π, `NaN` или бесконечностью отбрасывается:
  `wrap_angle()` (`utils.h`) на 1e30 и бесконечности не выходит из цикла, и
  один такой пакет повесил бы сервер (requirements.md, раздел 7);
- версия в `MSG_JOIN` проверяется по первым шести байтам, до размера:
  клиент другой версии с другой длиной `MsgJoin` получает `REJECT_VERSION`,
  а не молчание;
- `server_tick()` опрашивает транспорт и в начале, и в конце, поэтому
  снапшот уходит в том же тике, а не со следующим опросом;
- расписание снапшотов считается в целых тиках, а не в секундах `float`:
  сумма 1/60 расходится с 1/20, и снапшот время от времени съезжал бы на
  тик;
- зерно — `time(NULL)`, `srand()` вызывается в `server_create()`.
  В `MSG_ACCEPT.map` идёт имя файла карты без каталога; если оно не
  умещается в `NET_MAP_MAX`, сервер не создаётся;
- игрок получает клетку спавна по номеру своего слота, поэтому двое не
  стартуют в одной клетке.

Тест — `tests/test_net_server.c`, 23 случая по настоящим сокетам на
127.0.0.1. Сервер и боты, которые говорят на протоколе вручную, работают в
одном процессе, таймауты проверяются сдвигом часов ENet. Снапшоты тест
различает по `World.tick`, а не по тому, в какой тик пришла датаграмма,
поэтому от планировщика ОС он не зависит. 25 прогонов `ctest -j8` прошли без
единого падения. Тест ловит каждую из 11 подстановок в `net_server.c`: без
сложения нажатий, с повтором нажатий, без повтора ввода, без таймаута ввода,
с событиями одного тика, без очистки накопителя, с приёмом старого ввода,
без проверки версии, без `last_input_tick`, без опроса в конце тика, без
удаления игрока. Двенадцатая подстановка, без проверки угла, не роняет
тест, а вешает его в `wrap_angle()`. Покрыты все изменённые строки, кроме отказа `calloc()`. В
`test_net_protocol.c` добавлен тест `snapshot_set_events()`.

Критерии проверены на Linux:

- десять клиентов приняты с `id` 0–9, одиннадцатый получил
  `REJECT_SERVER_FULL` и отключён; на листен-сервере локальный игрок
  занимает слот наравне с остальными;
- `PROTO_VERSION + 1` получает `REJECT_VERSION`, в том числе с `MsgJoin`
  другой длины;
- в тесте замолчавший клиент живёт 4 с после последнего пакета и исчезает
  через 5,5 с, а его слот получает следующий клиент. Отдельно проверено двумя
  процессами (временная утилита, в проект не вошла: сервер в цикле 60 Гц со
  сном и 10 ботов в другом процессе на `level1.txt`). После `kill -9`
  процесса ботов сервер убрал всех десятерых в пределах 5 с, а новый процесс
  снова занял все десять слотов;
- тем же прогоном: ровно 60 тиков каждую секунду при 10 клиентах, тик в
  среднем 0,1 мс, худший 0,6 мс, опоздание тика не больше 0,27 мс (P4 —
  2 мс). В тесте без сна тик занимает 15 мкс в DM и 16–26 мкс в co-op;
- трафик с заголовками IPv4, UDP и ENet (40 Б на пакет): в тесте 73,6 КБ/с
  в DM (без врагов) и 153 КБ/с в co-op (`MAX_ENEMIES` врагов), двумя
  процессами на `level1.txt` — 80,8 КБ/с. Худший случай co-op, когда во всех
  снапшотах по 32 события, — 227 КБ/с, это выше N7. На такой случай и нужен
  `--snaprate`;
- пропущенный ввод не останавливает и не дёргает игрока: шаг за тик
  одинаков и в тике без ввода;
- выстрел в первом и во втором из трёх тиков между снапшотами есть в
  ближайшем снапшоте ровно один раз, в предыдущем и в следующем его нет.
