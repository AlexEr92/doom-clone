# 06-06 — Ввод на тик вместо ввода на кадр

**Этап:** 6 — Мультиплеерная логика локально
**Зависит от:** 06-01
**Блокирует:** 07-04, 08-02
**Оценка:** ~70 строк изменений

## Контекст

Сейчас ввод привязан к кадру, а не к тику симуляции:

- `main.c:170` — `input_end_frame()` вызывается **внутри** цикла фикс-шага,
  то есть все edge-события (`fire_pressed`, `use`, `switch1/2`) гасятся после
  первого под-шага
- `input.c:65` — `mouse_dx` накапливается за кадр, применяется в первом
  под-шаге, дальше нули
- `input.c:72-80` — `input_end_frame()` сбрасывает всё скопом

При 30 FPS на кадр приходится два тика, и второй получает пустой ввод.
Для сети нужен ровно один `PlayerInput` на тик, с номером тика — иначе
предсказание и реконсиляция не сойдутся.

## Замечания

Решение «угол считает клиент, сервер принимает как есть» — стандартное
(так делает Quake): поворот должен быть мгновенным, задержка на RTT в
повороте камеры неприемлема. Сервер угол не валидирует, только ограничивает
частоту вводов. Для демо на LAN этого достаточно.

Edge-флаги нельзя просто размазать по всем тикам кадра: `fire_pressed`,
попавший в два тика подряд, даст два выстрела с одного нажатия.

## Закрыто

2026-10-16 — ввод разделён по границе кадра и тика. `InputState` остался
сырым состоянием SDL за кадр и получил `angle` — угол, до которого клиент
довернул. `input_turn()` (`input.c`) раз в кадр, вне фикс-шага, переводит в
него `mouse_dx` (`MOUSE_SENS`) и клавиши A/D (`ROT_SPEED` на длительность
кадра). `input_sample(InputState *in, uint32_t tick)` внутри шага собирает
`PlayerInput` с маской `BTN_*` из тех же клавиш, что и раньше, и гасит
попавшие в него фронты — `fire_pressed`, `use`, `switch1/2`. `sample_input()`
из `main.c` ушёл.

`input_end_frame()` вызывается раз в кадр после всех тиков и гасит только
кадровое: `mute`, `pause_toggle` и остаток `mouse_dx`. Фронты тиков он не
трогает, поэтому в кадре без тиков нажатие доживает до следующего. Вне
`GSTATE_PLAYING` фронты сбрасывает `input_clear_edges()`, иначе нажатие на
паузе выстрелило бы в первом тике после неё.

`BTN_FIRE` ставится и по удержанию, и по фронту: зажатый курок стреляет в
темпе кулдауна оружия, как раньше, а нажатие, отпущенное раньше, чем его
увидел тик, всё равно даёт один выстрел.

`player_update()` принимает `const PlayerInput *` вместо `InputState`: угол
берёт из ввода через `wrap_angle()` и двигается по маске кнопок. Ни
`mouse_dx`, ни клавиш поворота в `PlayerInput` нет, так что прочитать их
`player_update()` не может. Мост `buttons_to_input_state()` в `world.c`
удалён.

`tests/test_input.c` проверяет:
- маску из тех же клавиш, без A/D;
- номер тика и угол в снимке;
- фронт ровно в одном из трёх тиков кадра при удержанных клавишах во всех
  трёх;
- зажатый курок в каждом тике;
- выстрел от нажатия, отпущенного до тика;
- фронт, переживший кадр без тиков;
- сброс фронтов без тика;
- поворот клавишами и мышью, свёртку угла и один угол на все тики кадра.

`tests/test_player.c` подаёт `PlayerInput`. Тесты поворота в нём заменены
двумя: игрок принимает угол из ввода как есть, а угол вне `[-π, π]`
сворачивается.

Проверено при ограничении FPS временным `SDL_Delay(40)` в копии дерева,
около 22 FPS:
- пять мгновенных нажатий пробела дали пять выстрелов, по одному тику с
  `BTN_FIRE` на каждое; без правки — один выстрел из пяти;
- одно мгновенное `E` перед дверью открыло её, и она осталась открытой —
  `BTN_USE` нёс ровно один тик;
- трассировка 479 тиков: в каждом кадре 2–3 вызова `input_sample()`, ровно
  по числу его тиков, номера 0…478 идут подряд.

Обзор мышью под Xvfb не работает, поэтому чувствительность проверена по
построению. Формула `-mouse_dx × MOUSE_SENS` за кадр не изменилась и
закреплена тестом, а итоговый угол за кадр тот же, что и раньше.

`ctest` (11 сюит), `driver.sh smoke`, `cppcheck` и `clang-format` проходят.
