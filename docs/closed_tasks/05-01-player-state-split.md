# 05-01 — Разделить `Player` на состояние и камеру

**Этап:** 5 — Развязка симуляции и рендера
**Зависит от:** —
**Блокирует:** 05-02, 05-03, 06-02, 07-03
**Оценка:** ~100 строк изменений

## Контекст

`player.h:10-16` смешивает симуляцию и рендер:

```c
typedef struct { float x, y; float dir_x, dir_y; float plane_x, plane_y; float hp, armor; } Player;
```

`plane_x/plane_y` — артефакт рендера (FOV 0.66), к игровой логике отношения не
имеет. Плюс векторы направления нельзя корректно интерполировать между
снапшотами, а углы — тривиально. В пакете это 4 float вместо 1.

## Что сделать

- [x] Ввести `PlayerState` в `player.h`:
  ```c
  typedef struct {
      uint8_t id;
      float x, y, angle;      /* angle в радианах */
      float hp, armor;
      int   alive;
      float respawn_timer;
  } PlayerState;
  ```
- [x] Ввести `Camera { float dir_x, dir_y, plane_x, plane_y; }` и функцию
      `void player_camera(const PlayerState *p, Camera *c);`
      (`dir = (cos a, sin a)`, `plane = FOV_PLANE * (sin a, -cos a)`)
- [x] `player_init()` — задавать `angle`, а не векторы (текущее
      `dir_x=-1, dir_y=0` → `angle = π`)
- [x] `player_update()` (`player.c:32-69`) — вместо поворота векторов
      прибавлять к `angle` и нормализовать в `[-π, π]`; движение считать от
      `cos/sin`, стрейф — от перпендикуляра
- [x] Поменять сигнатуры потребителей камеры на `const Camera *`:
      `raycast_render()`, `sprite_render()`
- [x] `weapon.c`, `enemy.c`, `door.c`, `item.c`, `hud.c` — на `PlayerState`

## Затрагиваемые файлы

`player.h/.c`, `raycast.h/.c`, `sprite.h/.c`, `weapon.h/.c`, `enemy.h/.c`,
`door.h/.c`, `item.h/.c`, `hud.h/.c`, `game.h/.c`, `main.c`

## Критерий готовности

- [x] Собирается без предупреждений (`-Wall -Wextra`)
- [x] Игра визуально и на ощупь не изменилась: движение, стрейф, мышь,
      скорость поворота те же
- [x] `PlayerState` не содержит ничего от рендера; `grep -n "plane" player.h`
      ничего не находит

## Замечания

Нормализация угла обязательна: без неё `angle` уплывёт за много минут игры
и потеряет точность float, а на этапе 8 сломает интерполяцию по кратчайшей
дуге.

## Закрыто

2026-08-22 — `Player` разделён на `PlayerState` (`player.h`) и `Camera`
(`camera.h`). В состоянии остались `id`, `x/y`, `angle`, `hp`, `armor`,
`alive`, `respawn_timer`; поворот прибавляется к `angle` и сворачивается в
`[-π, π]`, движение и стрейф считаются от `cos/sin`. `raycast_render()` и
`sprite_render()` принимают `const Camera *` дополнительным аргументом,
камера строится раз в кадр в `main.c`. `weapon.c`, `enemy.c`, `door.c`,
`item.c`, `hud.c`, `game.c` переведены на `PlayerState`; `door_try_use()`
берёт направление из `cosf/sinf` угла, `weapon_try_fire()` строит камеру
сам, потому что его экранный хитскан живёт до 05-04.

Три отступления от исходной формулировки:

- **Формула `plane` в задаче задавала не тот перпендикуляр.** С
  `FOV_PLANE * (-sin a, cos a)` и `angle = π` получалось `plane = (0, -0.66)`,
  тогда как рендер всегда работал с парой `dir = (-1, 0)`, `plane = (0, +0.66)`
  (соглашение lodev). Буквальное следование формуле зеркалило бы картинку по
  горизонтали и меняло местами клавиши стрейфа. В коде и в тексте задачи —
  `FOV_PLANE * (sin a, -cos a)`.
- **`Camera` живёт в отдельном `camera.h`, а не в `player.h`.** Иначе не
  выполняется собственный критерий задачи `grep -n "plane" player.h`; заодно
  заголовок симуляции остаётся без рендерных типов, что понадобится
  headless-сборке на этапе 7. `player_camera()` — `static inline` там же.
- **Скорость стрейфа сохранена как есть.** Старый код двигал игрока вбок по
  вектору `plane` длиной `FOV_PLANE`, то есть стрейф на треть медленнее
  ходьбы. Вынесено в `STRAFE_SPEED` (`player.c`), поведение не изменено;
  сама особенность заведена как bug-005.

Кадр спавна не совпадает со старым пиксель в пиксель: расходится 5652
пикселя из 1 024 000. Старая сборка воспроизводится побитово между
запусками, так что расхождение вносит именно этот переход. Все различия —
однопиксельные швы на границах текселей: на спавне игрок смотрит ровно
вдоль −X, `wallX * texW` попадает в целые числа, а `sinf(π) = -8.7e-8`
вместо нуля разрешает эти ничьи в другую сторону. Геометрия не сдвинута.
Это неустранимое следствие хранения направления углом; в игре незаметно, но
базовый скриншот для пиксельного сравнения в 05-03 надо снимать уже после
05-01.

Проверено: сборка без предупреждений под `-Wall -Wextra`,
`clang-format --dry-run -Werror` чист, `driver.sh smoke` проходит все шесть
проверок.

Движение сверено с прежней реализацией напрямую: обе слинкованы в одну
программу и прогнаны по одинаковой последовательности `InputState` на
открытой карте. Ходьба, стрейф в обе стороны, задний ход и комбинация
«вперёд + вбок» совпадают побитово; после поворотов накапливается
расхождение до 1e-5 клетки — тот же артефакт хранения направления углом.
Отдельно пройдена граница `+π`, на которой игрок стартует: угол корректно
сворачивается в `[-π, π]`.
