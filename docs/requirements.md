# Технические требования

Нефункциональные требования к doom-clone: производительность, сеть,
надёжность, лимиты, платформы, тестирование.

**Что этот документ не описывает.** Функциональность, игровые механики и
порядок работ — в [architecture.md](architecture.md) (как устроено сейчас) и
[roadmap.md](roadmap.md) (куда движемся). Конкретные шаги
реализации и критерии приёмки отдельных изменений — в [tasks/](tasks/).
Здесь — только те требования, которые нельзя восстановить из кода и которые
относятся к системе целиком.

Числовые значения констант — в `src/config.h` (единственный источник истины
в коде). Таблицы ниже фиксируют требования; значения в `config.h` обязаны
им соответствовать.

## 1. Платформы

| Тир | Платформы | Что гарантируется |
|---|---|---|
| Tier-1 | Linux (x86-64, glibc) | Собирается и проверяется при каждом изменении |
| Tier-2 | macOS (Intel/ARM), Windows (MinGW, MSVC) | Обязаны собираться; проверяются в конце каждого этапа плана |

- Сборка: CMake ≥ 3.15, компилятор с поддержкой C11 (gcc, clang, MSVC)
- Обязательные зависимости: SDL2, SDL2_mixer, ENet
- Сборка без предупреждений при `-Wall -Wextra` на tier-1
- Сборка с `-DENABLE_MULTIPLAYER=OFF` обязана работать на всех платформах
  и не требовать ENet
- Байт-порядок: предполагается little-endian (x86-64, ARM64). Big-endian
  не поддерживается; несовпадение отсекается проверкой `PROTO_VERSION`

## 2. Производительность

Целевое железо — десктоп или ноутбук последних ~10 лет. Специальных
требований к GPU нет: рендер программный, SDL используется только для
вывода готового кадра.

| ID | Требование | Значение |
|---|---|---|
| P1 | Частота кадров, клиент | ≥ 60 FPS при 1280×800, 10 игроков, карта 48×48 |
| P2 | Частота кадров, худший случай | ≥ 30 FPS (все игроки в кадре, открытое пространство) |
| P3 | Частота симуляции | 60 Гц, фиксированный шаг |
| P4 | Джиттер серверного тика | ≤ 2 мс; пропуск тиков не допускается |
| P5 | Нагрузка выделенного сервера | ≤ 25% одного ядра при 10 игроках |
| P6 | Память, клиент | ≤ 64 МБ RSS |
| P7 | Память, выделенный сервер | ≤ 32 МБ RSS |
| P8 | Время запуска до меню | ≤ 2 с |

Замеры P1/P2 проводятся при отключённом vsync. Текущая реализация создаёт
рендерер с `SDL_RENDERER_PRESENTVSYNC` (`engine.c:25`) — для измерений
нужен флаг запуска, отключающий vsync.

## 3. Сеть

Основной сценарий — локальная сеть. Игра через интернет должна работать,
но качество при высокой задержке гарантируется в ограниченном объёме.

| ID | Требование | Значение |
|---|---|---|
| N1 | Задержка: эталон | RTT ≤ 10 мс (LAN) — управление неотличимо от одиночной игры |
| N2 | Задержка: рабочий диапазон | RTT ≤ 150 мс — игра полноценно играбельна |
| N3 | Задержка: деградация | RTT 150–250 мс — допустимы видимые рывки чужих игроков |
| N4 | Задержка: не поддерживается | RTT > 250 мс |
| N5 | Потери пакетов | ≤ 5% — без видимых артефактов; ≤ 15% — играбельно |
| N6 | Трафик вниз, на клиента | ≤ 20 КБ/с |
| N7 | Трафик вверх, с сервера | ≤ 200 КБ/с при 10 игроках |
| N8 | Трафик вверх, с клиента | ≤ 3 КБ/с |
| N9 | Размер снапшота | ≤ 1400 Б — умещается в MTU без фрагментации |
| N10 | Частота снапшотов | 20 Гц, настраивается флагом запуска |
| N11 | Частота отправки ввода | 60 Гц |

Требования к окружению:

- Транспорт — UDP, порт 27015 по умолчанию, настраивается
- Работа за NAT: хост требует проброса порта. Обход NAT, UPnP и
  сервер-посредник в объём не входят
- Игра обязана работать без интернета и без внешних сервисов: никаких
  master-серверов, телеметрии, обновлений
- Симметричный NAT со стороны клиента (без проброса) должен работать —
  соединение инициирует клиент

## 4. Надёжность

| ID | Требование | Значение |
|---|---|---|
| R1 | Обнаружение отключения клиента сервером | ≤ 5 с |
| R2 | Обнаружение потери сервера клиентом | ≤ 5 с, с выходом на экран `CONNECTION LOST` |
| R3 | Освобождение слота отключившегося | Немедленно после R1; слот переиспользуется |
| R4 | Падение клиента | Не влияет на сервер и других игроков |
| R5 | Падение сервера | Клиенты корректно выходят в меню, без зависания и падений |
| R6 | Длительность матча без деградации | ≥ 30 минут непрерывной игры |
| R7 | Рассинхрон предсказания | Расхождение сходится к нулю; накапливающийся дрейф — дефект |

Отдельно: игрок никогда не должен оказаться внутри геометрии. Закрытие
двери в проходящем игроке, спавн в стене и «продавливание» стены при
реконсиляции — дефекты, а не допустимая деградация.

## 5. Лимиты и ёмкость

Все лимиты — статические массивы, динамическое выделение памяти в игровом
цикле не допускается.

| Сущность | Лимит | Обоснование |
|---|---|---|
| Игроков в матче | 10 | Размер снапшота и плотность карты |
| Врагов | 32 | Только co-op |
| Предметов | 64 | Ограничено маской `uint64_t` в снапшоте |
| Дверей | 64 | |
| Спрайтов (клиент) | 192 | Враги + предметы + бочки + 9 чужих игроков |
| Точек спавна | 24 | Требуется вдвое больше, чем игроков |
| Размер карты | 48×48 | |
| События в снапшоте | 32 | При переполнении — отбор по дистанции до получателя |
| История вводов (клиент) | 128 тиков (~2 с) | Реконсиляция |
| История позиций (сервер) | 64 тика (~1 с) | Лаг-компенсация |

Превышение любого лимита обязано обрабатываться явно (отказ в подключении,
отбрасывание, лог), а не приводить к порче памяти. Соответствие лимитов
формату снапшота контролируется `static_assert`.

## 6. Совместимость

- Протокол версионируется полем `PROTO_VERSION`; несовпадение версий —
  отказ в подключении с внятным сообщением, а не неопределённое поведение
- Совместимость между версиями протокола не поддерживается: клиент и
  сервер обязаны быть одной сборки
- Формат карты обратно совместим: карты без новых маркеров грузятся и
  работают в одиночной игре
- Файл настроек (адрес, порт, имя) — необязателен; его отсутствие или
  повреждение не мешает запуску

## 7. Безопасность

Модель угроз ограничена: игра рассчитана на доверенную локальную сеть,
защита от целенаправленного читерства в объём не входит.

Обязательный минимум:

- Сервер авторитетен: клиент не может задать себе позицию, здоровье,
  патроны или засчитать попадание
- Все входящие пакеты валидируются по длине и типу до разбора; некорректный
  пакет отбрасывается, соединение не роняет сервер
- Строковые поля (имя игрока, имя карты) обрабатываются с явной проверкой
  длины и завершающего нуля
- Имя карты из `MSG_ACCEPT` не используется как путь к файлу без проверки:
  только имя файла из `assets/maps/`, без переходов по каталогам
- Частота входящих пакетов ограничена; клиент, шлющий ввод чаще 60 Гц,
  не должен нагружать сервер

Угол поворота клиент задаёт сам и сервер его не валидирует — осознанный
компромисс ради отзывчивости управления.

## 8. Вне рамок

Явно не входит в объём работ: анти-чит, матчмейкинг и мастер-сервер,
голосовой чат, режим наблюдателя, запись и воспроизведение матчей,
сохранение статистики между матчами, командные режимы, модификации и
пользовательский контент, локализация интерфейса.

## 9. Тестирование

Основной способ — ручная проверка по критериям приёмки из task-файлов.
Автоматизируется только то, что глазами не ловится.

### Автоматические тесты

- **Replay-тест детерминизма** (`tests/replay_test.c`, вводится задачей
  06-01): два прогона `world_step()` с одной последовательностью вводов от
  одного состояния дают побитово одинаковый результат через 600 тиков.
  Это единственная защита от рассинхрона предсказания, который иначе
  обнаруживается только по симптомам
- **Проверка размеров структур протокола**: `static_assert` на
  `sizeof(MsgSnapshot)` и лимиты — срабатывает на этапе компиляции

### Ручная проверка

| Когда | Объём |
|---|---|
| Каждое изменение (tier-1) | Сборка без предупреждений, запуск solo, матч на 2 клиентах локально |
| Завершение задачи | Критерии приёмки из соответствующего task-файла |
| Завершение этапа | Матч на 4 клиентах, прогон при `--netlag 150 --netloss 5`, сборка на tier-2 |
| Готовность к релизу | Полный сценарий из раздела 10 |

### Инструменты

- Флаги `--netlag <ms>` и `--netloss <pct>` (задача 08-04) — основной способ
  воспроизвести сетевые условия; не требуют root и работают на всех платформах
- `tc netem` на Linux — для проверки того, что искусственные задержки
  клиента ведут себя так же, как настоящие
- Оверлей F3 — пинг, потери, расхождение предсказания, размер снапшота

## 10. Критерии готовности мультиплеера

Мультиплеер считается завершённым, когда выполнено всё перечисленное:

- [ ] Матч deathmatch на 10 клиентах длительностью 10 минут: без падений,
      рассинхрона, утечек памяти и накопленного дрейфа предсказания
- [ ] Все требования разделов 2–5 выполнены и измерены, а не оценены на глаз
- [ ] При `--netlag 150` управление отзывчиво, попадания по движущимся
      игрокам проходят, чужие игроки движутся плавно
- [ ] При `--netloss 15` игра остаётся играбельной
- [ ] Подключение и отключение любого клиента в любой момент не влияет
      на остальных
- [ ] Выделенный сервер работает на машине без дисплея ≥ 30 минут
- [ ] Сборка и запуск матча на каждой из tier-2 платформ
- [ ] Replay-тест проходит
- [ ] Человек с чистой машиной поднимает игру на двоих по README без
      дополнительных вопросов
